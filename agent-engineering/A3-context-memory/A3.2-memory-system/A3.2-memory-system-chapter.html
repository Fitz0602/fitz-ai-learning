A3.2 Memory 机制（四层架构）

从"每次对话从零开始"到"跨会话持续进化" — Agent 记忆系统的工程全景

🔗 主线连接：状态持久化 → KBA 项目经历的理论化（回答问题7：如何管好模型能看到什么？）

§1 是什么：为什么 LLM 需要 Memory

💡 核心直觉

Memory is what turns a model into a product.

没有 Memory 的 Agent：

  • 每次交互从零开始——不记得你是谁、做过什么、偏好是什么
  • 不能从错误学习——上次踩过的坑，这次照踩不误
  • 重复同样错误——同样的无效策略反复尝试
  • 无法累积知识——每次对话产生的洞察随 session 结束而蒸发

LLM 本质是无状态的：API 返回那一刻所有对话信息消失。Memory 系统就是要在无状态的计算原语之上，构建有状态的产品体验。

1.1 无状态本质 vs 有状态产品需求

LLM API 的调用模型是纯粹的无状态函数：

# LLM 本质上就是一个纯函数
response = llm(messages=[...])  # 输入 messages，输出 response
# 调用结束 → 内部状态全部丢弃
# 下次调用 = 全新的推理过程，对过去一无所知

但用户期望的产品体验是高度有状态的：

维度LLM 的现实（无状态）用户的期望（有状态）
身份认知每次都是陌生人"你还记得我叫 Fitz 吗？"
上下文延续每轮只知道 system prompt + 当前消息"上周我们讨论的方案进展如何？"
错误规避同样的错误可以无限重复"上次这个参数设成 3 失败了"
能力成长模型权重固定，不会因为使用而变强"用久了应该更懂我"
偏好适应每次都用默认风格回复"我喜欢简洁的回答，别啰嗦"
⚠️ 常见误区

误区："把历史对话全塞进 Context Window 不就行了吗？"

这确实是最简单的"记忆"方案，但它有三个致命限制：

  1. Context Window 是有限资源——128K tokens 看似很大，但塞进 50 轮对话 + 工具定义 + System Prompt 后所剩无几
  2. "大海捞针"效应——上下文越长，模型定位关键信息的准确率越低（业界观测约在 32K tokens 后显著下降）
  3. 成本线性增长——每轮对话都要重新发送全部历史，token 成本随对话长度线性放大

这就是为什么我们需要一个分层的、结构化的记忆系统，而不是粗暴地把一切塞进上下文。

1.2 Memory ≠ 存储，Memory = "在正确的时间回忆起正确的信息"

很多人把 Memory 系统简单理解为"数据库"。这是一个危险的简化。

传统数据库Agent Memory 系统
存进去就能取出来存了不一定能取出来——需要 recall 机制
查询精确匹配需要 语义检索——"上次类似的失败经验"
数据是静态的记忆需要 衰减、更新、遗忘
存储和读取解耦写入时机和读取时机同等重要
一致性是核心目标相关性 > 一致性——模糊匹配优于精确空结果
💡 Memory 系统的四维设计空间

设计一个 Memory 系统，本质上是在回答四个问题：

  1. 存什么（What）：不是所有东西都值得记。原始对话 vs 提炼后的摘要 vs 结构化三元组？
  2. 怎么存（How）：向量库？知识图谱？全文索引？Markdown 文件？各有取舍。
  3. 何时取（When）：每次都取？用户触发时取？Agent 判断需要时取？这是影响 token 成本的关键杠杆。
  4. 怎更新（Update）：追加式？覆盖式？冲突检测？记忆衰减（forgetting curve）？

§2 怎么实现：四层记忆架构

2.1 架构总览

受人类认知科学启发，工业界已形成一套四层记忆架构共识。每层有不同的生命周期、存储介质和访问模式：

2.2 第一层：主上下文（Main Context）— Prompt 窗口内的"现场"

这是最基础也最容易理解的一层。当前这一轮推理所需的一切信息，都在 Prompt 里。

例 1：一个典型 ReAct 循环的主上下文构成
<system>
你是一个外汇分析助手。当前时间：2026-05-27
可用工具：get_exchange_rate, search_news, format_report
</system>

<user>
帮我查一下 USD/CNY 最新汇率，并分析近一周趋势
</user>

<assistant>
Thought: 用户需要汇率查询和趋势分析。先获取最新汇率。
FunctionCall: get_exchange_rate(from="USD", to="CNY")
</assistant>

<tool_result>
{"rate": 7.2451, "amount": 1.0, "updated_at": "2026-05-27T09:30:00Z"}
</tool_result>

↑ 以上全部 = Main Context（约 ~400 tokens）
= System Prompt + User Message + Assistant Thought
  + Function Call + Tool Output

关键约束：Main Context 受限于模型的 Context Window 大小（4K ~ 1M+ tokens，取决于模型）。它是最"昂贵"的存储——每个 token 都要经过完整的注意力计算。

2.3 第二层：工作上下文（Working Context）— 会话内的"短期记忆"

当一个会话超过几十轮后，不可能把所有历史都放在 Main Context 中。工作上下文的职责是在会话范围内维护一个"压缩版的历史"。

三种主流实现方案

方案原理优点缺点代表
滑动窗口
(Sliding Window)		只保留最近 N 轮对话实现极简，零延迟丢失早期重要信息LangChain ConversationBufferWindowMemory
对话摘要
(Summarization)		旧对话压缩为摘要，保留近期原文信息密度高，保留关键语义摘要质量依赖 LLM，有信息损失LangChain ConversationSummaryMemory
向量检索
(Vector Retrieval)		历史向量化存储，按语义相似度召回可精确定位相关片段需要 embedding + 向量库基础设施LlamaIndex / Mem0
例 2：滑动窗口 + 摘要混合策略（生产常用）
class WorkingContext:
    """会话级工作上下文管理"""
    
    def __init__(self, window_size: int = 10, summary_threshold: int = 20):
        self.window_size = window_size          # 最近 10 轮保持原文
        self.summary_threshold = summary_threshold  # 超过 20 轮触发摘要
        self.recent_messages: list[Message] = []   # 滑动窗口区
        self.summary: str = ""                     # 摘要区
    
    def add_message(self, msg: Message):
        self.recent_messages.append(msg)
        
        # 超过阈值 → 把最早的批次压缩为摘要
        if len(self.recent_messages) > self.summary_threshold:
            batch = self.recent_messages[:self.window_size]
            new_summary = llm.summarize(
                previous_summary=self.summary,
                new_messages=batch
            )
            self.summary = new_summary
            self.recent_messages = self.recent_messages[self.window_size:]
    
    def build_prompt_context(self) -> str:
        """组装注入 Prompt 的工作上下文"""
        parts = []
        if self.summary:
            parts.append(f"[之前的对话摘要]\n{self.summary}")
        parts.extend(m.to_string() for m in self.recent_messages)
        return "\n".join(parts)

# 效果：
# 第 1-10 轮：全部原文 (~2000 tokens)
# 第 11-20 轮：摘要(~300 tokens) + 最近10轮原文 (~2000 tokens)
# 第 21-30 轮：更新摘要(~400 tokens) + 最近10轮原文 (~2000 tokens)
# → 无论聊多久，Prompt 中的上下文量基本恒定

2.5 第四层：程序性记忆（Procedural Memory）— 持续进化的"技能库"

这是最高阶也最容易被忽视的一层。前三层管的是"知道什么"，第四层管的是"会做什么"。

程序性记忆对应人类的肌肉记忆——骑自行车不需要每次都回忆平衡原理，弹钢琴不需要看乐谱。同理，一个成熟的 Agent 在处理同类任务时，应该能复用已经学会的工作流模式，而不是每次都从第一性原理重新推理。

§3 为什么：Token 经济学约束下的最优记忆策略

3.1 核心矛盾：记忆是有代价的

在设计 Memory 系统时，有一个永恒的张力：

⚖️ 记忆系统的核心权衡

更多信息 → 更好的决策质量（理论上）

更多信息 → 更高的 Token 成本 + 更低的注意力效率（实际上）

这不是一个"越多越好"的问题，而是一个优化问题：在有限的 Token 预算下，选择业务价值密度最高的信息子集放入上下文。

3.2 ENGRAM 方法论：1% Token 达到 Full-Context 效果

2025 年学术界提出的 ENGRAM 方法（NeurIPS 2025 Spotlight）给出了一个惊人的结论：

通过精心设计的记忆检索策略，仅需约 1% 的 full-context tokens 就能达到接近完整上下文的 baseline 效果。

— ENGRAM: Efficient Neural Generative Reterieval Augmentation (NeurIPS 2025)

这意味着什么？如果你的 full-context 是 100K tokens，ENGRAM 方法只需要 ~1K tokens 的精选记忆就能达到几乎相同的效果。核心原则不是"存越多越好"，而是"存对的最小集合"。

3.3 四个决策变量（重新审视）

回到 §1.2 提出的四个问题，现在用 Token 经济学的镜头重新审视：

变量" naive 做法"经济学最优"做法节省幅度
存什么 (What)保存原始对话全文只存提炼后的原子事实 + 经验教训~90% 存储压缩
怎么存 (How)全部存向量库分层存储：事实→图谱，经验→MD，对话→向量~70% 检索加速
何时取 (When)每次都全量取出按需检索：只在 Agent 判断相关时才取~80% Token 节省
怎更新 (Update)只追加不删除衰减 + 冲突检测：旧信息降权，矛盾事实标记~50% 质量提升
✅ Token 经济学的三条铁律
  1. 密度优先于数量：一条精确的结构化事实 > 10 条原始对话片段
  2. 检索时机是最大杠杆：从"每次全量加载"改为"按需检索"，Token 消耗可降低一个数量级
  3. 遗忘是一种特性而非 bug：不是所有记忆都有永久价值。合理的遗忘曲线（forgetting curve）能让记忆系统保持在最佳效能状态

3.4 一个具体的成本模型

假设你的 Agent 日活 1000 用户，平均每会话 20 轮：

## 方案 A：暴力全量上下文（Naive）
每轮 tokens = System(500) + History_avg_10rounds(4000) + Tool_output(1000) 
             + Response(500) = ~6000 tokens/轮
每日总 tokens = 1000 users × 20 rounds × 6000 = 120M tokens
月度成本 (@ $3/M tokens input) = **$10,800/月**
额外问题：上下文超长 → 准确率下降 ~15%

## 方案 B：四层记忆架构（Optimized）
每轮 tokens = System(500) + WorkingContext_summary(800) 
             + Recent_3rounds(1200) + Retrieved_memory(600) 
             + Tool_output(1000) + Response(500) = ~4600 tokens/轮
每日总 tokens = 1000 × 20 × 4600 = 92M tokens
月度成本 (@ $3/M) = **$8,280/月** （省 23%）
额外收益：上下文精炼 → 准确率提升 ~12%（记忆质量补偿）

## 方案 C：ENGRAM 式极致优化（Advanced）
每轮 tokens = System(500) + WorkingContext_compressed(400) 
             + Recent_1round(400) + Top5_retrieved_facts(300) 
             + Tool_output(1000) + Response(500) = ~3100 tokens/轮
每日总 tokens = 1000 × 20 × 3100 = 62M tokens  
月度成本 = **$5,580/月**（省 48%）

更重要的是准确率的非线性提升——方案 C 因为注入的信息都是经过筛选的高密度事实，模型决策质量反而高于方案 A。

4.3 ChatGPT vs Claude：两种记忆模式的逆向工程对比

通过逆向分析和公开文档研究，工业界两大头部产品的记忆策略呈现出截然不同的设计哲学：

💡 设计哲学背后的工程取舍

ChatGPT 选择被动注入，是因为它的主要场景是短问答——大部分用户问完就走，预计算记忆的开销可以摊薄。而且 OpenAI 有强大的基础设施来维持数十亿用户的记忆索引。

Claude 选择主动检索，是因为 Anthropic 定位的核心场景是深度工作——编程、写作、研究等需要长时间上下文的任务。让模型自己判断"我现在需要记忆吗"，虽然增加了一轮 tool call 的延迟，但换来了更高的 precision 和更好的 token 利用率。

对你的 Agent 来说：如果场景偏向高频短交互（如 FXAgent 汇率查询），ChatGPT 模式更合适；如果偏向长周期复杂任务（如 KBAgent 知识生产），Claude 模式更合适。最好的架构往往是混合式的。

5.1 KBA 项目中的记忆挑战

回顾你在 67 天内交付 KBA 项目的经历，记忆系统设计是贯穿始终的核心挑战之一：

1

每家银行的监管要求、字段格式、审批流程都不一样。Agent 如何"记住"这些差异并在正确的场景应用正确的规则？

4

Skill 之间需要共享什么记忆？各自应该维护什么私有记忆？边界在哪里？

5.2 KBA 记忆架构映射

5.3 HQA 就是结构化的情景记忆

KBA 产出的 443 条 HQA，本质上是结构化的情景记忆（Structured Episodic Memory）：

例 5：一条 HQA 如何同时充当情景记忆和语义知识
{
    "hqa_id": "hqa-27244-127",
    "question": "跨境汇款的 SWIFT Code 格式要求是什么？",
    "answer": "SWIFT Code（也称 BIC）由 8 或 11 位字符组成：
           - 8 位：银行代码(4) + 国家代码(2) + 地区代码(2)
           - 11 位：8 位 + 分行代码(3)
           示例：BKCHCNBJ（中国银行总部），
                 BKCHCNBJ110（中国北京分行）",
    
    # === 情景记忆属性 ===
    "created_at": "2026-04-15",
    "created_in_session": "kb-session-042",
    "source_topic": "跨境支付-汇款流程",
    "extraction_method": "三段式流水线-Phase2",
    
    # === 语义记忆属性 ===
    "tags": ["swift-code", "跨境汇款", "银行格式"],
    "related_topics": ["topic-27252-swire", "topic-27251-remittance"],
    "confidence": 0.94,
    "verified_by": "human-review-pass"
    
    # === 程序性记忆属性 ===
    "quality_checks_passed": ["has_specific_numbers", "cites_example", 
                               "under_200_chars", "not_generic"]
}

一条 HQA 同时承载了三种记忆类型的信息——这正是好的记忆系统设计的标志：一次写入，多层复用。

5.4 DDAgent 的跨主体记忆隔离

在 DDAgent（尽调 Agent）的场景中，有一个 KBA 没有的特殊挑战：跨主体的记忆隔离。

⚠️ DDAgent 的记忆安全挑战
p>DDAgent 同时服务于多个尽调客户（不同基金公司、不同标的企业）。如果记忆系统不做隔离：
  • A 客户的敏感尽调结论可能泄漏给 B 客户
  • 甲企业的风险标签可能错误地关联到乙企业的报告中
  • 不同客户的偏好设置互相污染

解决方案：命名空间（Namespace）隔离 + 行级权限控制

隔离维度实现方式技术选型
客户级隔离 每个客户 ID 作为向量集合（Collection）的前缀或独立命名空间 Qdrant Collection per client / Pinecone Namespace
项目级隔离 同一客户下的不同尽调项目的记忆互不可见 Metadata Filter: {"client_id": "X", "project_id": "Y"}
敏感等级分级 不同敏感等级的记忆采用不同的存储和检索策略 PUBLIC → 向量检索；CONFIDENTIAL → 加密图谱；SECRET → 仅内存

5.5 从 KBA 到通用 Agent 记忆框架的设计启示

✅ A3.2 核心结论
  1. Memory is what turns a model into a product——没有记忆系统，LLM 永远只是"每次从零开始的函数"，无法成为真正有用的产品
  2. 四层架构是工业界共识：Main Context → Working Context → External Context → Procedural Memory，每层解决不同时间尺度和粒度的记忆需求
  3. Token 经济学是核心约束：不是存越多越好，而是通过"存什么/怎么存/何时取/怎更新"四维决策，找到最小有效记忆集合
  4. ChatGPT（被动注入）vs Claude（主动检索）代表了两种哲学：前者适合高频短交互，后者适合深度长周期任务；混合式架构往往是最终答案
  5. KBA 的 443 条 HQA 就是 structured episodic memory 的最佳实践：一条数据同时承载情景/语义/程序性三种记忆属性，Skill URLs 是持久化记忆的工程载体
  6. 跨主体隔离是企业级 Agent 的必修课：DDAgent 的 namespace 隔离模式可直接推广到任何 multi-tenant 场景
