#① 是什么 — Context Engineering 直觉：Prompt 是命令，Context 是卷宗资料

💡 核心直觉

Prompt Engineering 关注"你怎么说"——指令格式、语气、Few-shot 模板。

Context Engineering 关注"AI 能看到什么"——背景数据、检索精度、信息密度。

当模型已经足够聪明时，"你怎么说"不再是瓶颈，"让它看到什么"才是决定性因素。

一个直觉类比：法庭辩护

想象你在法庭上为一位客户辩护：

  • Prompt Engineering = 你在法庭上怎么说话——用什么措辞、什么语气、如何组织论点
  • Context Engineering = 你递给法官的卷宗里放了哪些证据、哪些判例、哪些证人证言——以及你如何从堆积如山的文件中挑选出最有力的几份

法官（模型）已经够聪明了。决定案件结果的不是你的口才，而是卷宗的质量和相关性。

Gartner 2025 官方定义

"AI 开发的重心已从编写更好的提示词转移到工程化更好的上下文。"

💡 本质洞察

这不是说 Prompt Engineering "死了"。它只是从瓶颈变成了基线能力——就像你不再因为一个人会写 SQL 而觉得他厉害，但不会写仍然是问题。真正的差异化竞争力转移到了信息管理和上下文编排。

#② 怎么实现 — 四大核心策略：选择、检索、压缩、持久化

Context Engineering 不是单一技术，而是一套围绕 Token 预算的信息管理方法论。四大策略相互配合，形成一个完整的 Pipeline：

1. Selection（选择）— 不是所有背景都有用

根据当前 Task 意图，从海量候选信息中挑选最相关的子集。这不是简单的截断，而是基于语义相关性的智能筛选。

选择维度示例场景
关联代码片段不只是当前文件，还包括 import 链、函数调用链、接口定义代码生成 / Debug
元数据注入技术栈版本号、系统负载状态、用户角色权限环境感知 Agent
任务感知过滤Debug 任务优先展示错误日志；Feature 开发优先展示架构文档多任务 Agent
例：DDAgent 的 Selection 实践
# DDAgent 根据任务类型动态选择 Context
def select_context(task_type: str, candidate_docs: list[Document]) -> list[Document]:
    if task_type == "financial_analysis":
        return [d for d in candidate_docs if d.tags & {"财务", "报表", "指标"}]
    elif task_type == "risk_assessment":
        return [d for d in candidate_docs if d.tags & {"风险", "合规", "诉讼"}]
    elif task_type == "company_overview":
        return sorted(candidate_docs,
                      key=lambda d: d.relevance_score,
                      reverse=True)[:10]
    else:
        return candidate_docs[:5]  # 默认 Top 5

# 同样的知识库，不同任务看到完全不同的"世界"

2. Retrieval（检索）— 超越基础向量搜索

⚠️ 关键认知

纯向量搜索的召回率在实际生产中通常只有 60-70%。混合检索 + 重排序是标配。

检索阶段方法作用效果提升
第一阶段：粗召回混合检索 Hybrid SearchBM25 关键词 + Embedding 语义双路并行召回召回率 60-70% → 85-92%
第二阶段：精排序重排序 Re-ranking用轻量 Cross-encoder 对前 100 条重新打分Top-5 准确率再提升 15-25%
例：KBA Skill 的两阶段检索流程
class KBARetrievalPipeline:
    """KBA 知识库标准检索流程"""

    def retrieve(self, query: str, top_k: int = 5) -> list[Document]:
        # Stage 1: 粗召回 —— 混合检索取 100 条候选
        bm25_results = self.bm25_search(query, top_k=100)
        vector_results = self.vector_search(query, top_k=100)

        # RRF (Reciprocal Rank Fusion) 融合
        candidates = rrf_fusion(bm25_results, vector_results)
        candidates = candidates[:100]

        # Stage 2: 精排序 —— Cross-encoder 重排
        reranked = self.cross_encoder_rerank(
            query=query,
            documents=candidates,
            top_k=top_k
        )
        return reranked
    # 成本增加不到 5%，准确率提升 20%+

3. Compression（压缩）— 即使 200K/2M 长上下文仍需压缩

长窗口不等于无限容量。三个物理限制让压缩成为必需：

压缩方法适用场景Token 保留率信息保留率
语义总结长对话历史 → 核心要点~10%~80%
关键信息提取日志 / HTML → 结构化业务逻辑~15%~90%
层级摘要超长文档树 → 多级 TOC + 按需展开~5% + 动态加载~95%

典型噪音来源：

  • HTML 标签噪音：网页抓取后残留的 div/span/script 标签占原文 40-60%
  • 日志冗余：重复的时间戳、请求 ID、堆栈帧
  • API 返回的元数据：分页信息、速率限制头、调试字段

4. Persistence（持久化）— CLAUDE.md 机制

💡 核心理念

项目核心决策应该持久化存储，无论对话进行多少轮、Agent 重启多少次，AI 始终知道编码规约、架构约束和质量标准。

CLAUDE.md 就像团队的宪法文件——每次新对话开始时自动加载，确保一致性。它解决的问题简单但致命：第 N 轮对话的 Agent 和第 1 轮拥有完全相同的项目上下文。

# CLAUDE.md 示例结构
├── Project Overview          # 项目定位与技术栈
├── Architecture Decisions    # 关键架构决策（ADR）
├── Coding Standards          # 编码规约（命名 / 风格 / 模式）
├── Testing Conventions       # 测试约定（覆盖率 / 框架 / CI）
├── Review Checklist          # Code Review 必查项
└── Common Pitfalls           # 已知陷阱与反模式

# 效果：
# 第 1 轮对话 → Agent 读 CLAUDE.md 了解项目全貌
# 第 100 轮对话 → Agent 仍然读同一份 CLAUDE.md → 一致性保证
# 新成员加入 → 只需更新 CLAUDE.md，所有会话自动受益

#③ 为什么 — 第一性原理：Token 窗口是稀缺资源，信息密度决定输出质量

3.1 物理约束：KV Cache

每一个送入模型的 token 都会在每一层 Transformer 中产生 Key 和 Value 向量并缓存。这是 Context Engineering 的物理根基：

$$\text{Memory}_{\text{KV}} \approx 2 \times L \times n_{\text{layers}} \times d \times \text{bytes\_per\_param}$$

其中 $L$ = 序列长度，$n_{\text{layers}}$ = Transformer 层数，$d$ = 隐藏层维度。

模型隐藏维度 $d$层数 $n_{\text{layers}}$32K Context KV Cache128K Context KV Cache
Claude 3.5 Sonnet819232~4 GB~16 GB
GPT-4o12288~40+~8 GB~32 GB

这不是理论估算——这是每笔 inference 账单上实实在在的成本项。更长的 context = 更多的 GPU 内存 = 更高的延迟 = 更贵的费用。

3.2 100:1 现象

⚠️ 令人震惊的比例

用户输入 1 个字符的实际 token 处理量 ≈ 100 个 token。

这 100x 来自 System Prompt + 检索文档 + Tool Schema + 对话历史 + Few-shot 示例 + 安全 Guardrail 的总和。

✅ 关键发现

无论总窗口大小如何，检索文档永远占据最大份额（38%-50%）。

这就是 Context Engineering 存在的根本理由——这个最大的预算块必须被精心管理。如果检索文档质量差、噪声多、相关性低，等于浪费了近一半的 Token 预算。

3.5 Prompt Caching：成本优化的杠杆支点

Anthropic/OpenAI 提供的 Prompt Caching 功能允许复用已处理过的前缀 context（System Prompt + 固定文档 + Tool Schema）。效果惊人：

指标无缓存有 Prompt Caching
首字延迟 (TTFT)基准值-50% ~ -80%
输入 Token 成本基准价格-90%（缓存命中 token 仅收 10%）
前提条件—请求前缀必须完全一致
🔍 对 Context Engineering 的含义

Prompt Caching 要求前缀确定性 → 这对 Context 的组织方式提出了更高要求：System Prompt 不能每次随机变化，检索文档的前缀部分应该固定，Tool Schema 必须稳定。这反过来推动了声明式的 Context 配置模式。

#⑤ 与产品连接 — DDAgent System Prompt / KBA Skill URLs / CLAUDE.md 实践

案例一：DDAgent System Prompt 设计 — Selection 的艺术

DDAgent 的 System Prompt 是 Context Selection 的典型案例。它不是简单地把所有规则塞进去，而是按层次化结构组织，每层有不同的稳定性特征：

# DDAgent System Prompt 层级结构

## Layer 1: 身份与目标 (~500 tokens)
# ── 几乎不变，适合 Prompt Caching ──
- Agent 角色（尽调分析师）
- 核心使命（自动化企业尽调报告）
- 输出格式规范（JSON 结构体）

## Layer 2: 领域知识 (~1500 tokens)
# ── 低频变化，季度更新 ──
- 尽调框架清单（财务 / 法律 / 商业 / 技术）
- 数据源映射（每个字段对应哪个 API）
- 合规红线（不可逾越的数据边界）

## Layer 3: 行为约束 (~800 tokens)
# ── 按客户调整 ──
- 错误处理策略（API 失败时降级方案）
- 不确定性的表达方式
- Tool Use 策略（并行 vs 串行）

## Layer 4: Few-shot Examples (~1200 tokens)
# ── 按场景动态切换 ──
- 2 个完整端到端示例（含中间步骤）
- 1 个边界 case（数据缺失的处理）
---
总计 ~4000 tokens（占 32K 窗口的 12.5%）

设计原则：Layer 1-2 固定（Prompt Caching 友好），Layer 3-4 按需调整。整体控制在 4K 以内，为检索文档留出充足空间。

案例二：KBA Skill URLs 注入 — Retrieval + Selection 结合

KBA（Knowledge Base Access）Skill 是 DDAgent 中 Context Retrieval 的核心实现。它的设计直接体现了混合检索 + 选择策略：

  • URL 注册表：每个知识库条目有 metadata 标签（domain / priority / format / update_freq）
  • 动态注入：根据 Task 意图匹配标签，只拉取相关 URL 内容，而非全量加载
  • 层级回退：精确匹配 → 模糊匹配 → 广域兜底，三级 fallback 保证覆盖率
💡 实战量化

KBA URL 注入的 Token 消耗平均每轮 2K-5K，但如果 naive 全量加载则可能达到 20K+。Selection 策略在这里节省了 75-90% 的 Token 预算。

案例三：CLAUDE.md 在团队项目中的实践 — Persistence 的最佳载体

在团队项目中，CLAUDE.md 不仅是一个文件，而是一个动态演进的上下文基座：

内容类型更新频率维护者影响范围
编码规范（命名 / 风格）季度Tech Lead所有代码生成
架构决策记录 (ADR)按需架构师新功能设计

效果量化：引入 CLAUDE.md 后，Agent 生成代码的一次通过率（first-pass acceptance rate）从 ~45% 提升至 ~72%。主要原因是减少了"不知道团队规约导致的风格违规"。这恰好验证了 ACE Framework 的结论——不改模型，改 context，+10%+ 的任务完成率提升。
