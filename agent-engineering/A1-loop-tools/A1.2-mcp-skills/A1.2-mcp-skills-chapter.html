A1.2 MCP 协议 · Tools vs Skills

工具标准化 + 能力封装 — 从"给模型一把锤子"到"教模型一套手艺"

§1 是什么：从 N×M 到 N+M

💡 PM 直觉类比

想象你在管一个跨境支付中台。每接入一家新支付渠道（支付宝、PayPal、Stripe），你都要为每家写一套独立的适配器——参数格式不同、签名算法不同、错误码不同。接 5 家渠道 × 3 个业务线（收单/汇款/退款），就是 15 个适配器。

MCP 就是这个问题的答案：一套协议，所有 AI 客户端和所有工具服务都按同一套规则对话。就像 USB-C 口——不管什么设备，插上就能用。

1.1 A1.1 留下的尾巴：Tool 从哪来？

上一章我们讲了 ReAct 循环 + Function Calling——模型决定调用哪个函数，Runtime 执行后把结果喂回来。但有一个关键问题被刻意跳过了：

⚠️ A1.1 的未解之谜

Tool 的定义从哪里来？谁负责描述"有哪些工具可用"？模型怎么知道它能调 search_database 但不能调 drop_table？

这就是 A1.2 要回答的核心问题：工具的定义、发现、标准化。

1.2 一个真实场景：DDAgent 的工具链

以你的 DDAgent（尽调 Agent） 为例，它需要调用这些能力：

能力类型数据来源调用方式
搜索企业工商信息API 调用天眼查/企查查HTTP GET
查询企业风险标签数据库内部 MySQLSQL SELECT

📌 DDAgent 的 MCP 工具定义（伪代码）
# ddagent_mcp_server.py  —  DDAgent 的 MCP Server
from fastmcp import FastMCP

mcp = FastMCP("ddagent-tools")

# ===== Tool: 执行操作 =====

@mcp.tool()
def search_enterprise(name: str, limit: int = 5) -> list[dict]:
    """搜索企业基本信息。输入企业全名或关键词，返回匹配列表。
    用于尽调流程的第一步：定位目标企业。"""
    return tianyancha_api.search(name, limit)

@mcp.tool()
def query_risk_tags(company_id: str) -> dict:
    """查询企业的风险标签集合。输入企业唯一标识 ID，
    返回诉讼/被执行/经营异常等风险标签及详情。"""
    return db.execute(
        "SELECT tag_type, detail, severity FROM risk_tags "
        "WHERE company_id = %s ORDER BY severity DESC",
        (company_id,)
    )

@mcp.tool()
def route_to_human_review(report_id: str, priority: str = "normal") -> dict:
    """将尽调报告路由到人工复核队列。输入 report_id 和优先级，
    返回工单号和预计处理时间。"""
    return wecom.create_ticket(
        title=f"尽调复核-{report_id}",
        priority=priority,
        queue="due_diligence_review"
    )

# ===== Resource: 读取数据 =====

@mcp.resource("config://report-template")
def get_report_template() -> str:
    """当前使用的尽调报告 Markdown 模板内容。"""
    return s3.read("templates/dd-report-v3.md")

@mcp.resource("data://industry-benchmarks")
def get_industry_benchmarks() -> str:
    """各行业的关键财务指标基准值（JSON 格式），
    用于对比目标企业与行业平均水平。"""
    return json.dumps(load_benchmarks())

# ===== Prompt: 提示词模板 =====

@mcp.prompt()
def due_diligence_workflow(company_name: str) -> str:
    """尽调工作流的标准操作程序（SOP）。引导 Agent 按顺序执行：
    1) 企业信息搜索 → 2) 风险标签查询 → 3) 行业对标分析
    → 4) 报告生成 → 5) 路由复核。"""
    return f"""你是 DDAgent 尽调助手。现在对「{company_name}」执行完整尽调。

## 标准流程
Step 1: 用 search_enterprise 获取基础信息
Step 2: 用 query_risk_tags 获取风险画像
Step 3: 读取 resource data://industry-benchmarks 进行行业对标
Step 4: 读取 resource config://report-template 填写报告
Step 5: 如有高风险标签，调用 route_to_human_review

## 输出要求
- 结构化 Markdown 报告
- 高风险项必须标红并附证据链接
- 最终给出风险等级：低/中/高"""

if __name__ == "__main__":
    mcp.run()  # 一行启动，所有 MCP Client 都能用

这段代码做了什么？它把 DDAgent 的 5 种异构能力统一暴露为一个标准的 MCP Server。不管是 Claude Desktop、Cursor 还是你自己的 Python Agent Runtime，只要支持 MCP 协议，就能直接调用这些工具——零适配成本。

✅ 核心要点
  • Tool= 函数，模型能做的事（搜索、查询、路由）
  • Resource= 数据，模型能读的东西（模板、基准值）
  • Prompt= 模板，模型应该遵循的工作流（SOP）
  • MCP Server = 把这三者打包成一个标准接口，所有客户端通用

2.2 三原语逐一击破（每个都有完整代码示例）

🔧 原语一：Tool — 让 AI 执行操作

Tool 是最常用的原语。本质上就是一个带类型注解和 docstring 的 Python 函数，通过 @mcp.tool() 装饰器注册。

例 1：FXAgent 的汇率查询工具
# fx_rate_mcp.py  —  换汇 Agent 的 MCP 工具
from fastmcp import FastMCP
from typing import Literal

mcp = FastMCP("fx-rate-server")

@mcp.tool()
def get_exchange_rate(
    from_currency: str,
    to_currency: str,
    amount: float = 1.0,
    date: str | None = None  # 可选：历史日期 YYYY-MM-DD
) -> dict:
    """查询实时或历史汇率。

    Args:
        from_currency: 源货币代码（如 USD, CNY, HKD）
        to_currency: 目标货币代码
        amount: 兑换金额，默认 1.0（返回汇率本身）
        date: 可选，指定历史日期查询当日收盘价

    Returns:
        包含 rate, amount, updated_time 的字典

    Example:
        用户问"100美元换多少人民币？" →
        get_exchange_rate(from_currency="USD", to_currency="CNY", amount=100)
    """
    rate = forex_api.get_rate(from_currency, to_currency, date)
    return {
        "rate": rate,
        "from": from_currency,
        "to": to_currency,
        "amount": amount * rate,
        "updated_at": rate.timestamp,
        "date": date or "live"
    }

# 关键设计决策：
# 1. 类型注解 (str, float, Literal) → MCP 自动生成 JSON Schema
# 2. docstring → 成为 LLM 看到的工具"说明书"
# 3. 默认参数 → LLM 不传时自动使用
# 4. 返回 dict → 客户端可渲染为结构化卡片

注意 docstring 的写法——这不是给人看的注释，而是 LLM 决定是否调用此工具的唯一依据。写得越好，工具选择越准。

例 2：TRSAgent 的售后分类工具（含枚举约束）
# trs_mcp.py  —  售后 Agent 的分类工具
from fastmcp import FastMCP
from enum import Enum

class TicketCategory(str, Enum):
    REFUND = "refund"           # 退款
    EXCHANGE = "exchange"       # 换汇
    RATE_QUERY = "rate_query"   # 汇率咨询
    TECHNICAL = "technical"     # 技术问题
    OTHER = "other"             # 其他

class UrgencyLevel(str, Enum):
    P0 = "P0"  # 紧急（资金卡住）
    P1 = "P1"  # 高（影响用户体验）
    P2 = "P2"  # 一般（咨询类）

mcp = FastMCP("trs-classifier")

@mcp.tool()
def classify_ticket(
    user_message: str,
    user_history: list[str] | None = None,
    order_id: str | None = None
) -> dict:
    """将用户售后消息分类为工单类别和紧急程度。

    这是 TRSAgent 的第一步：在进入 ReAct 循环之前，
    先对用户意图做一次精确分类，后续循环只加载对应类别的工具集。

    Args:
        user_message: 用户原始消息文本
        user_history: 可选，最近 N 条历史消息（帮助消歧）
        order_id: 可选，关联订单号（如有）

    Returns:
        category (TicketCategory): 工单类别
        urgency (UrgencyLevel): 紧急程度
        confidence (float): 分类置信度 0-1
        reasoning (str): 分类依据摘要
    """
    # 这里可以调用内部分类模型，或直接让 LLM 做 structured output
    result = classifier_model.predict(user_message, history=user_history)
    return result

# 设计要点：
# - Enum 类型 → MCP Schema 自动变成下拉选项，LLM 只能从中选择
# - 可选参数 → LLM 根据上下文自行判断是否传入
# - 这个 Tool 本身也可以是一个 LLM 调用（嵌套 Agent 模式）

📦 原语二：Resource — 给 AI 读取的数据源

Tool 是"动作"（POST），Resource 是"数据"（GET）。当模型需要的不是执行操作，而是参考信息时用 Resource。

例 3：BAAgent 的经营分析数据资源
# ba_mcp.py  —  经营分析 Agent 的 MCP 数据层
from fastmcp import FastMCP

mcp = FastMCP("ba-data-layer")

# === 静态 Resource（URI 固定，不需要参数）===

@mcp.resource("config://ba/report-schema-v3")
def get_report_schema() -> str:
    """BAAgent 月度经营报告 v3 的字段定义和数据口径说明。
    Agent 在生成报告前必须先读取此 resource，确保格式合规。"""
    return """
## BAAgent Report v3 Schema

### 必填字段
- `executive_summary` (str): 150字以内执行摘要
- `key_metrics` (dict): 核心指标表 {GMV, transaction_count, avg_ticket_size}
- `trend_analysis` (list): 趋势分析段落列表（至少 3 个维度）
- `risk_alerts` (list): 风险预警条目

### 数据口径
- GMV = 成交金额（不含退款）
- Transaction count = 成功交易笔数

Resource 和 Tool 的本质区别：

维度ToolResource

📝 原语三：Prompt — 预定义工作流模板

Prompt 原语是三者中最容易被低估的。它不是给用户的提示词，而是给 LLM 的 SOP（标准操作程序）——告诉模型"面对这类任务时，你应该按什么步骤、用什么工具、遵循什么规范来执行"。

例 4：KBAgent 的知识库生产 Prompt
# kb_mcp.py  —  知识库 Agent 的 MCP Prompt
from fastmcp import FastMCP

mcp = FastMCP("kb-workflow")

@mcp.prompt()
def kb_production_pipeline(topic: str, depth: str = "standard") -> str:
    """知识库三段式流水线的标准 SOP。

    引导 Agent 按"主题挖掘 → HQA 提取 → 主题关联"三步走，
    生产出高质量的知识库条目。depth 可选 standard/deep/quick。

    已产出成果：86 条主题 + 443 条 HQA（截至 2026-05）
    """
    return f"""# KBAgent 知识生产 SOP v2

## 任务：为「{topic}」生产知识库条目
## 深度模式：{depth}

### Phase 1: 主题挖掘 (Topic Mining)
1. 用 search_knowledge_base("{topic}") 检索已有相关主题
2. 用 web_search("{topic} 最新动态") 获取外部最新信息
3. 判断是否需要新建主题还是更新现有主题
4. 输出 topic_id + title + summary (3 句话以内)

### Phase 2: HQA 提取 (High-Quality Q&A Extraction)
1. 基于 Phase 1 的主题内容，提取用户最可能问的问题
2. 每个问题必须满足：
   - 是真问题（有人真的会这么问，不是自问自答）
   - 有明确答案（不是"视情况而定"）
   - 可独立存在（不依赖阅读上下文）
3. 对每个 HQA 生成：question + answer(200字内) + tags[] + related_topics[]

### Phase 3: 主题关联 (Topic Linking)
1. 用 link_topics() 将新主题与已有主题建立关联
2. 更新主题图谱中的边关系
3. 输出最终的主题网络变化

### 质量门禁
- 每个主题至少 3 个 HQA
- answer 中必须包含具体数字或引用来源
- 禁止空泛表述（如"请参考官方文档"）

### 输出格式
```json
{{"topics_created": N, "hqas_created": M, "links_added": L}}
```"""

# 使用效果：
# 用户说"帮我把'离境退税'加入知识库"
# Agent 加载此 Prompt → 自动按三步走 → 产出结构化结果
# 比每次手写 prompt 效率高 3-5 倍，且质量一致性好很多

2.4 完整通信流程：一行用户请求背后的 7 步

当用户在 Claude Desktop 里说 "帮我查一下腾讯控股的最新汇率风险"，背后发生了什么？

1
用户输入 → Host (Claude Desktop) 接收消息
2
初始化 → Host 创建 MCP Client，Client 与 Server 建立 JSON-RPC 会话（握手）
3
工具发现 → Client 向 Server 发送 tools/list 请求，Server 返回所有可用 Tool 定义（名称 + 参数 Schema + 描述）
4
LLM 推理 → Host 将用户消息 + Tool 列表一起发给 LLM，LLM 决定调用 get_exchange_rate(from="HKD", to="CNY")
5
工具调用 → Client 向 Server 发送 call_tool JSON-RPC 请求，Server 执行函数逻辑
6
结果回传 → Server 将执行结果包装成 MCP 格式返回 Client → Host → 注入 LLM 上下文
7
继续推理 → LLM 基于结果组织自然语言回复用户（可能触发下一轮 ReAct 循环）
💡 第 3 步是 MCP 的灵魂

工具发现（Tool Discovery）是 MCP 区别于硬编码 Function Calling 的核心。Server 不是静态地预定义一组工具——它可以动态地根据认证身份、权限级别、甚至上下文来决定暴露哪些工具。这意味着：

  • 普通用户看到 5 个工具，管理员看到 15 个
  • 测试环境看到 mock 工具，生产环境看到真实工具
  • 工具列表可以随时间演化而不改 Client 代码

§3 为什么是 MCP 而不是别的方案

3.1 第一性原理：工具集成问题的本质

问题本质：AI Agent 需要对接的外部能力是异构的（API / DB / 文件 / 工作流）、演进的（新增工具 / 改接口 / 废弃旧能力）、多方参与的（工具提供方 ≠ Agent 开发方 ≠ 用户）。

数学表达：假设有 $N$ 个 AI Client 和 $M$ 个工具服务，没有标准协议时的适配工作量是 $O(N \times M)$；有了统一协议后降为 $O(N + M)$。

📐 Token 经济学视角

纯 Tools 架构的一个致命问题：Context Window 爆炸。

假设你有 100 个工具，每个工具的平均 Schema 描述消耗 ~200 tokens。一次性加载全部 = 20,000 tokens——这还没算用户对话本身。而 GPT-4o 的 128K context 里塞进 20K 的工具定义，模型的注意力会被严重稀释，工具选择准确率断崖下降（业界观察约下降 15-25%）。

MCP 的渐进式披露（Progressive Disclosure）解决了这个问题——初始只加载工具名称和一句话描述（~20 tokens/个），详细 Schema 按需加载。

3.2 为什么 MCP 赢了（vs 其他候选方案）

方案提出方核心思路现状致命缺陷
Function CallingOpenAI (2023)JSON Schema 定义工具广泛使用每家格式不同，需逐家适配
LangChain ToolsLangChain (2023)Python 类封装 @tool 装饰器生态丰富绑死 Python 生态，非标准协议
OpenAPI/SwaggerSmart (2019)REST API 描述语言成熟稳定为人类设计的，LLM 用起来笨重
MCPAnthropic (2024.11)JSON-RPC + 三原语 + 渐进披露事实标准生态仍在快速迭代中
Google A2AGoogle (2025)Agent-to-Agent 协作协议早期解决的是不同问题（Agent 间协作而非工具调用）

MCP 胜出的原因不是技术最先进，而是时机 + 设计权衡恰到好处：

  1. 开放但有用：Anthropic 开源后 6 个月内 OpenAI、Google 全部跟进（2025 年初完成），避免了"又一套私有协议"
  2. 三层抽象粒度合适：Tool/Resource/Prompt 三原语覆盖了 90% 的实际需求，不多不少
  3. 开发者体验好：FastMCP 让一个 Python 函数变 MCP 工具只需要加一个装饰器
  4. 双模传输：stdio 满足个人开发者，Streamable HTTP 满足企业级部署
⚠️ MCP 不是银弹
  • 调试困难：JSON-RPC 是黑盒的，出了问题要靠日志拼凑
  • 安全边界模糊：Tool 执行的是真实代码，LLM 传入恶意参数怎么办？需要 Server 层做校验
  • 版本兼容：协议本身在快速演进（SSE → Streamable HTTP → Stateless），老 Server 可能被废弃
  • 性能开销：每轮工具调用多了一层序列化/反序列化（但对大多数场景可忽略）

4.2 Tools vs Skills：本质区别（带代码对比）

这是本章最重要的概念区分。Tool 回答"能做什么"，Skill 回答"怎么做"。

对比：同一个"代码审查"能力，Tool 版 vs Skill 版
# ========== Tool 版本（原子能力）==========

@mcp.tool()
def read_file(path: str) -> str:
    """读取指定路径的文件内容。"""
    return open(path).read()

@mcp.tool()
def run_linter(file_path: str, ruleset: str = "default") -> list[dict]:
    """对文件运行 lint 检查，返回问题列表。"""
    return linter.run(file_path, ruleset)

@mcp.tool()
def run_tests(project_path: str, pattern: str = "test_*.py") -> dict:
    """运行项目测试套件，返回通过/失败/跳过统计。"""
    return pytest_runner.run(project_path, pattern)

# 问题：LLM 知道有这 3 个 Tool，但不知道：
# - 应该先 read_file 还是直接 run_linter？
# - linter 结果有问题时该修还是该跳过？
# - 测试失败了要不要阻止合并？

# ========== Skill 版本（能力包）==========
#
# SKILL.md  —  这就是 Skill 的核心文件
# （类似一本"使用手册"，LLM 通过阅读它学会整套流程）
#
---
name: code-review-skill
version: "1.2"
description: "自动化代码审查技能包，涵盖风格检查、安全扫描、测试验证"

## 你是谁
你是一位高级代码审查工程师。你的目标是找出代码中的实际问题（bug、安全隐患、性能陷阱），而不是挑剔风格。

## 审查流程（必须按顺序执行）

### Step 1: 文件读取与理解
- 调用 Tool: read_file(file_path)
- 先理解代码意图，不要急着找问题

### Step 2: 自动化检查（并行执行以下两个 Tool）
- 调用 Tool: run_linter(file_path, ruleset="strict")
- 调用 Tool: run_security_scan(file_path)

### Step 3: 测试验证
- 调用 Tool: run_tests(project_path, pattern="test_*")
- 如果测试失败，标记为 MUST_FIX

### Step 4: 输出审查报告
按以下格式输出：

| 严重度 | 类型 | 位置 | 描述 | 建议修复 |
|--------|------|------|------|----------|
| CRITICAL/MAJOR/MINOR/INFO | bug/security/perf/style | 行号 | 一句话 | 具体建议 |

## 判断准则
- CRITICAL: 数据丢失、安全漏洞、生产故障 → 必须阻塞合并
- MAJOR: 逻辑错误、性能退化 → 强烈建议修复
- MINOR: 风格不一致、命名不规范 → 建议修复但不阻塞
- INFO: 纯建议，可以忽略

## 反模式（不要做的事）
- ❌ 不要在没有理解代码意图的情况下提 issue
- ❌ 不要对纯风格问题标记为 CRITICAL
- ❌ 不要修改代码（只审查，不改）

4.3 渐进式披露（Progressive Disclosure）：Skill 的杀手级特性

这是 Skill 架构最精妙的设计。回顾上面说的 Context Window 问题：

例 6：渐进式披露的实际效果
# 假设你的 Agent 有 50 个 Skill（不是 50 个 Tool！）

# Level 0: Agent 启动时 —— 只加载元数据 (~5 tokens/skill)
# LLM 看到的：
skills = [
    {"name": "code-review",      "desc": "自动化代码审查"},
    {"name": "due-diligence",   "desc": "企业尽调流程"},
    {"name": "financial-analysis","desc": "经营数据分析"},
    {"name": "customer-service", "desc": "售后工单处理"},
    # ... 共 50 个，总计 ~250 tokens
]

# Level 1: 用户问"帮我 review 一下这个 PR" —— 加载 Skill 详情 (~2000 tokens)
# LLM 动态读取 code-review/SKILL.md，获取完整的审查流程、判断准则、反模式

# Level 2: 审查过程中需要参考数据 —— 按需加载 Resource
# 读取 resource config://lint-rules / security-checklist 等

# 对比：如果是 50 个 Tool 全量加载
# 50 × 200 tokens = 10,000 tokens（仅工具定义！）
# 而 Skill 模式下：250 (L0) + 2000 (L1, 仅 1 个 skill) + 500 (L2) = ~2750 tokens
# 节省 72% 的 context space

这就是为什么 Anthropic 的 Agent Skills 架构强调 "像专家一样工作——不需要背诵所有法律条文，只需要知道去哪里查阅"。

你的 Harness 框架（Goal / Boundary / Trigger / Action / Gate / Evaluate）和 MCP Skill 天然互补：

Harness 组件对应 MCP 概念实际落地

✅ A1.2 核心结论
  1. MCP 解决的是工具集成的 $O(N \times M)$ 问题，让 N 个 Client 和 M 个 Server 只需各实现一份协议
  2. 三原语（Tool/Resource/Prompt）覆盖 90% 场景：执行操作、读取数据、工作流模板
  3. Skill 是更高层封装：Tool = 锤子，Skill = 木匠手艺（知道何时用什么锤子 + 怎么用）
  4. 渐进式披露是杀手级特性：从 ~10K tokens（全量 Tool）降到 ~2.5K（Skill 按需加载），节省 72% context
  5. 对你的 6 个 Agent 来说：MCP 化的最大收益不在"技术上更酷"，而在团队协作（新人读 SKILL.md 就能上手）和复用（FX 的汇率 Server 可以同时给 DDAgent 和 BAAgent 用）
