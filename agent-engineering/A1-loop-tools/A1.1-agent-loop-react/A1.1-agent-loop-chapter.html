① 是什么：LLM 不再只是聊天机器人

直觉类比

把 Agent Loop 想象成一个新入职的跨境支付运营专员。

以前你问 ChatGPT 一个问题，它就像一个只能口头回答的顾问——知道汇款流程、懂外汇政策，但不会自己去查系统、不会自己发邮件、不会自己去核对一笔订单的状态。

Agent Loop 做的事情是：给这个运营专员一台电脑和一套操作权限，让他不仅能"说"，还能"做"。他可以查系统获取实时数据、调 API 执行换汇操作、读数据库确认订单状态——然后基于这些操作的真实结果继续思考和决策。

核心区别只有一句话：从单次文本输出变成循环的"思考→行动→观察→再思考"。

Agent 的公式

Lilian Weng（OpenAI）在 2023 年给出了至今仍被广泛引用的 Agent 公式：

$$ \text{Agent} = \text{LLM} + \text{Memory} + \text{Planning} + \text{Tool\ Use} $$

Agent Loop 就是把这个公式变成可运行的代码——它是把 LLM 的单次推理能力包装进一个 while 循环里，让模型在每次迭代中决定：

步骤模型自问产出
Thought 思考我现在该做什么？自然语言推理过程（不给用户看）
Action 行动调用哪个工具？参数是什么？结构化的函数调用请求
Observation 观察工具返回了什么结果？真实的执行结果 JSON/文本

三个前置概念

在深入 ReAct 之前，先理解它融合了哪两种更早的能力：

能力做什么缺什么
Chain-of-Thought (CoT) 让模型"展示思考过程"，分步推理复杂问题 盲于现实世界 —— 只能用训练数据里的知识，无法获取新信息
Tool Calling 让模型输出结构化的函数调用请求，由外部代码执行 没有规划 —— 模型不知道何时调用、为何调用、调用后怎么办
ReAct（本题主角） 交替进行推理和工具调用，每次观察后重新规划 两者融合 —— 既能思考又能行动，且行动结果反馈回思维过程
关键洞察

Anthropic 工程团队的官方描述精准地概括了这个模式："Agents can handle sophisticated tasks, but their implementation is often straightforward. They are typically just LLMs using tools based on environmental feedback in a loop."

翻译成人话：Agent 听起来很高级，但本质就是 LLM + 工具 + 循环。所有复杂性来自工具设计和终止逻辑，而非架构本身。

② 怎么实现：ReAct 循环的解剖学

2.1 ReAct 的三步循环

ReAct 由 Princeton 和 Google Research 的 Yao 等人于 2022 年提出（ReAct: Synergizing Reasoning and Acting in Language Models）。核心思想极简：

一次迭代的三块内容：

Thought（思考）

模型的自由文本推理。例如："用户想换汇，我需要先查询当前汇率，再确认用户的换汇额度。"

关键点：Thought 不是写给用户看的，而是给模型自己的"工作笔记"。它决定了下一步 Action 的合理性。

Action（行动）

结构化的工具调用请求。例如：query_exchange_rate(from="USD", to="HKD")

关键点：Action 不是模型自己执行的——它只输出"我想调用这个函数"，由你的代码（runtime）真正执行。这就是 Function Calling 的核心契约。

Observation（观察）

工具执行后的结果，原样回传给模型。例如：{"rate": 7.7823, "timestamp": "2026-05-21T18:00:00Z"}

关键点：Observation 必须是真实的执行结果，不能被篡改或省略。否则模型会基于错误信息做出后续决策——这是生产环境最常见的 Bug 来源之一。

2.2 伪代码：整个循环不到 10 行

这是所有 Agent Loop 框架的核心骨架，无论 OpenAI SDK、Anthropic SDK 还是 LangChain，底层都是这段逻辑：

messages = [{"role": "user", "content": user_request}] while True: response = call_llm(messages, tools=tool_schemas) if response.finish_reason == "tool_use": results = execute_tools(response.tool_calls) # 并行执行多个调用 messages.append(response) # Thought + Action 追加到上下文 messages.append(results) # Observation 追加到上下文 else: return response.content # Final Answer → 退出循环
生产环境的 3 个必加守卫
  1. 最大迭代次数限制：默认 ≤ 10 次/轮。防止模型陷入无限工具调用循环（runaway loop），导致费用失控。
  2. 工具失败必须返回错误结果：永远不要因为工具报错就跳过 tool_result。缺失的 tool_result 会导致 API 校验错误；错误的 tool_result（如空字符串）会导致模型幻觉式编造答案。
  3. 并行工具调用：当模型一次返回多个 tool_calls 时，应并发执行以减少总延迟 50-70%（来源：LLMversus Production Architecture, 2026）。

【示例】FXAgent 的真实 ReAct 循环（Python + Anthropic SDK）

光有伪代码不够——来看 FXAgent（40万月活，AI采纳率 98-99.75%）的真实代码骨架：

import anthropic client = anthropic.Anthropic() # FXAgent 工具定义：查询实时汇率 FX_TOOLS = [ { "name": "query_fx_rate", "description": "查询指定币对的实时汇率。仅在用户明确需要汇率信息时调用。", "input_schema": { "type": "object", "properties": { "from_currency": {"type": "string", "description": "源币种，如 USD/CNY/HKD"}, "to_currency": {"type": "string", "description": "目标币种"} }, "required": ["from_currency", "to_currency"] } } ] def fx_agent_loop(user_message: str) -> str: """FXAgent 核心：短循环 ReAct（通常 1-2 轮）""" messages = [{"role": "user", "content": user_message}] for iteration in range(5): # 守卫：最多 5 轮（FX 场景通常 1-2 轮够用） response = client.messages.create( model="claude-sonnet-4-20250514", max_tokens=1024, system="你是跨境支付换汇助手。简洁回答，给出汇率后直接给建议。", messages=messages, tools=FX_TOOLS, ) # 提取 stop_reason 决定下一步 if response.stop_reason == "end_turn": return response.content[0].text # 最终答案 → 直接返回用户 # tool_use → 执行工具 → 将 Observation 追加回消息列表 for block in response.content: if block.type == "tool_use": result = execute_fx_query(block.input) # 调 tpg-fx-rate skill messages.append({"role": "assistant", "content": [block]}) messages.append({ "role": "user", "content": [ {"type": "tool_result", "tool_use_id": block.id, "content": json.dumps(result, ensure_ascii=False)} ] }) return "抱歉，处理超时，请重试。" # 达到最大迭代次数仍未结束
代码解读

注意这个循环和伪代码的对应关系：

  • `for iteration in range(5)` → 最大迭代守卫。FXAgent 高频场景下 5 轮绰绰有余，实际平均 1.2 轮
  • `response.stop_reason` → Anthropic 的循环控制字段（对应 OpenAI 的 `finish_reason`）
  • `messages.append(assistant) + messages.append(tool_result)` → 关键！必须把模型的 Action 和工具的 Observation 都追加进去，形成闭环
  • `system` prompt → 控制回复风格。FXAgent 用"简洁回答"确保高采纳率

2.3 Function Calling：模型与外部世界的契约

ReAct 能运转的基础设施是 Function Calling（OpenAI 术语）/Tool Use（Anthropic 术语）。这是一套三方契约：

角色职责产出物
你（开发者） 定义工具清单（name + description + JSON Schema 参数） tools[] 数组
LLM 根据上下文判断是否/何时/如何调用哪个工具 tool_use block（含函数名 + 参数 JSON）
Runtime 解析调用请求，执行实际操作，返回结构化结果 tool_result message block

【示例】DDAgent 的工具定义（多工具编排）

DDAgent（83% 预填率）需要比 FXAgent 复杂得多的工具集——它要做企业尽调，涉及多个数据源：

DDAGENT_TOOLS = [ # Tool 1: 查询企业工商信息（Knotel API） { "name": "query_company_info", "description": ( "查询企业的工商注册信息（法人、注册资本、成立日期、经营范围）。" "输入企业全名或统一社会信用代码。仅在做企业背景调查时调用。" ), "input_schema": { "type": "object", "properties": { "company_name": {"type": "string"}, "credit_code": {"type": "string", "description": "统一社会信用代码，优先于公司名使用"} }, "required": ["company_name"] ⚠️ credit_code 可选但推荐提供 } }, # Tool 2: 查询财务报表（多期对比） { "name": "query_financials", "description": ( "查询企业最近 3 年财务报表（营收、净利润、资产负债率、现金流）。" "返回标准化 JSON 格式的财务数据。用于评估企业偿债能力和盈利稳定性。" ), "input_schema": { "type": "object", "properties": { "company_id": {"type": "string", "description": "Knotel 内部企业 ID"}, "years": {"type": "integer", "description": "查询最近 N 年，默认 3"} }, "required": ["company_id"] } }, # Tool 3: 法律风险扫描 { "name": "scan_legal_risks", "description": ( "扫描企业的法律诉讼、行政处罚、失信记录。" "重点关注合同纠纷、劳动争议、税务违规。返回风险等级和具体案件数。" ), "input_schema": { "type": "object", "properties": { "company_id": {"type": "string"} }, "required": ["company_id"] } }, ] # ⭐ 关键设计要点： # 1. description 写了"何时调用"+"不调用场景"——大幅减少误触发 # 2. 参数有明确的中文 description —— 模型靠这个理解语义 # 3. credit_code 标记为可选但有优先级提示 —— 灵活但不模糊 # 4. 3 个工具覆盖 DDAgent 尽调流程的 3 个核心维度
工具定义的艺术

模型完全依赖 description 来决定何时调用工具。上面 DDAgent 的例子展示了三个关键设计原则：

  • 描述要包含"何时用"和"何时不该用"——减少无效调用 60%+
  • 参数 description 要写人类能读懂的说明——不是给程序员看的，是给模型看的
  • 工具粒度要匹配任务粒度——一个工具做一件事（单一职责），而不是一个万能工具

Anthropic 数据显示：添加基础工具后在 LAB-Bench 和 SWE-bench 上通常超越人类专家基准（来源：Anthropic Tool Use 文档, 2026.04）。

2.4 stop_reason / finish_reason：循环的生命线

每次 LLM 调用的返回值中都有一个关键字段，决定了循环的命运：

值含义你的动作
tool_use 模型要调用工具 执行工具 → 将 result 作为 tool_result 追加到 messages → 继续循环
end_turn 模型给出最终答案 读取 content，退出循环，返回给用户
max_tokens 达到输出上限 截断处理或重新发送（带提示"请继续"）
refusal 模型拒绝执行 检查内容策略或换个方式提问

【示例】TRSAgent 的 stop_reason 分支处理

TRSAgent（售后邮件分类 92.2%、准确率 93.2%）对每种 stop_reason 有不同的业务处理逻辑：

def trs_agent_loop(email_text: str) -> dict: """TRSAgent 核心：长循环 ReAct + 错误恢复""" messages = [build_trs_prompt(email_text)] classification = {} loop_count = 0 while loop_count < 10: # TRSAgent 可能需要更多轮次（KB检索+分类+生成回复） loop_count += 1 response = client.messages.create( model="claude-sonnet-4-20250514", max_tokens=2048, messages=messages, tools=TRS_TOOLS, # classify_email + search_kb + query_order ) if response.stop_reason == "end_turn": # ✅ 正常退出：提取分类结果和回复草稿 final_text = response.content[0].text classification["reply_draft"] = final_text break elif response.stop_reason == "tool_use": # 🔧 执行工具调用（可能多个并行） for block in [b for b in response.content if b.type == "tool_use"]: try: result = execute_trs_tool(block.name, block.input) # ⚠️ 关键：即使工具报错也要返回结构化错误信息 messages.append({"role": "assistant", "content": [block]}) messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": json.dumps(result, ensure_ascii=False) }] }) except Exception as e: # 🚨 工具异常时返回错误而非跳过——防止消息格式校验失败 messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": f"工具执行错误: {e}", "is_error": True # 标记为错误，帮助模型理解 }] }) elif response.stop_reason == "max_tokens": # ⚠️ 输出截断：将已有内容作为前缀继续生成 messages.append({ "role": "assistant", "content": response.content }) messages.append({ "role": "user", "content": "[请继续完成上一步未完成的回复]" }) else: # refusal 等 return {"error": f"模型停止原因: {response.stop_reason}"} return classification
TRSAgent 教训：3 个 P0 Bug 都在循环环节

上面代码看起来正确，但 TRSAgent 实际运行中发现的问题都在循环的细节里：

  • P0-1 充值 T+1 规则遗漏：Thought 阶段选错了工具（没先查 KB 就直接分类）→ 修复：在 tools description 中强调"必须先调用 search_kb"
  • P0-2 忽略链边界：Build Prompt 时把独立邮件当连续对话 → 修复：每封邮件初始化新的 messages 列表
  • P0-3 系统错误混淆：不同工具的错误码格式不一致 → 修复：统一 tool_result 格式为 `{status, error_code, message}`

③ 为什么：第一性原理——为什么必须是"循环"？

3.1 单次调用的根本缺陷

传统的 LLM 交互是一问一答：

单次调用的三大死穴：

死穴 1：知识截止

模型的训练数据有明确截止日期。它不知道今天发生了什么，不知道你公司系统的当前状态，不知道用户刚刚提交的那笔汇款的实时状态。单次调用无法突破这个天花板。

死穴 2：无法执行

LLM 的输出只是文本。发邮件需要调用邮件 API，查数据库需要 SQL，改文件需要文件系统操作。模型本身永远不会触碰这些系统。

死穴 3：无法多步规划

真实任务往往需要多步：先查状态 → 再确认规则 → 最后执行操作。单次调用无法在上一步的结果基础上自动启动下一步。

3.2 为什么 ReAct 而非其他模式？

ReAct 只是设计空间中的一个点。理解它的定位，才能知道什么时候用它、什么时候不用它：

模式形状优势劣势适用场景
Pure CoT Reason → Answer 便宜、快速 看不到外部世界 数学推理、逻辑题
Tool-calling only Act → Answer 简单查询快 无规划，容易误触发 简单 API 查询（天气、汇率）
ReAct Reason ↔ Act ↔ Observe 平衡通用，可自适应 可能循环多次，成本较高 大多数 Agent 场景（默认选择）
Plan-and-Execute Plan once → Act many 高效、确定性 计划错了全盘崩溃 步骤明确的任务
Reflection Act → Evaluate → Retry 能从错误中学习 需要显式的 critique 信号 代码生成、写作优化

第一性原理总结

ReAct 的本质价值在于信息闭环：模型不再是在真空中生成文本，而是每一步行动都获得真实世界的反馈，然后用这些反馈修正下一轮推理。

这恰好对应了贯穿主线中的 问题5（如何让模型主动行动？）——答案是：给它一个循环，让它在每次循环中获得新的观测数据，从而逐步逼近正确答案。

Oracle Blog（2026）的精辟总结：六大 AI 公司（OpenAI/Anthropic/Google/Microsoft/Meta/LangChain）虽然命名不同、SDK 不同、哲学不同，但底层执行模式完全一致——LLM + tools in a loop。差异在工具目录和终止逻辑，不在拓扑。

4.3 2025-2026 关键进展

Programmatic Tool Calling（Anthropic，2025）

Claude 不再逐个输出 tool_use block，而是写一段 Python 脚本来编排整个工作流。

效果：Token 减少 37%，推理次数减少 19+ 次/任务（来源：Zylos Research, 2026.01）。本质是把"多次串行 tool calling"压缩成一次脚本执行。

适用场景：复杂的多步骤任务（如 DDAgent 尽调流程中的多子Agent协调）。

Advanced Tool Use 套件（Anthropic，2025.12）

MCP 协议发布一年后发现的问题：它只提供了统一的工具接口，但没有规定 Agent 如何发现、选择、组合这些工具。当企业挂载上百个内部工具时，Agent 会"迷路"。

Advanced Tool Use 补齐了这块拼图：工具发现（Tool Search）+ 组合策略 + 容错机制。（详见下一章 A1.2 MCP协议）

Constrained Decoding 成为主流（2025）

确保 LLM 输出的工具调用严格符合 JSON Schema：

  • Outlines：FSM-based，97% success rate，0.4% hallucination
  • XGrammar：Pushdown automaton 支持复杂语法
  • llguidance：超快速（50μs CPU/token）
MCP 成为事实标准（2025-2026）
  • 2024.11：Anthropic 发布 MCP 规范
  • 2025.03：OpenAI 宣布支持 MCP → 标准之争结束
  • 2025年中：Google/Microsoft 接入；npm 月下载超 5000 万
  • 2025.12：Anthropic 将 MCP 捐赠给 Linux Foundation Agentic AI Foundation
  • 2026.01：月下载约 9700 万；Registry 超 20,000 个 MCP Server
  • 被称为 "USB-C for AI"——一个连接器通吃所有 AI 产品
当前未解决问题（2026）
  1. 认证标准缺失：MCP 无内置 auth 规范，每个 server 各自为战
  2. 运行时发现：Agent 无法在运行时搜索和选择最合适的 MCP server
  3. 成本与计费：协议不含定价信息，Agent 无法在做工具选择时考虑成本
  4. 工具数量诅咒：挂载工具越多，Agent 性能反而下降（上下文污染 + 选择困难）

⑤ 与产品连接：Fitz 的生产级 Agent 全是 Agent Loop 实例

理解了 Agent Loop 的抽象机制后，回头看 Fitz 正在管理的 Agent 项目——每一个都是 ReAct 模式的具体实例化。

5.2 【示例】DDAgent 的两层循环架构

DDAgent 是最复杂的案例——它在 ReAct 之上又包了一层 Planning：

def ddagent_dispatch(due_diligence_request: dict) -> dict: """ DDAgent 外层：Plan-and-Execute（Dispatcher） 流程： 1. 接收尽调需求 2. LLM 拆分子任务（主体信息 / 财务 / 法律 / ...） 3. 为每个子任务分配内层 ReAct Agent 4. 收集结果 → 预填表单 → 验证完整性 """ # Step 1: 外层 LLM 做规划（Plan 阶段，不需要工具） plan_response = client.messages.create( model="claude-sonnet-4-20250514", max_tokens=2048, system="你是尽调任务拆分专家。将需求拆分为独立的子任务。", messages=[{ "role": "user", "content": f"拆分以下尽调任务: {json.dumps(due_diligence_request)}" }], ) sub_tasks = parse_sub_tasks(plan_response.content[0].text) # Step 2: 并行启动内层 ReAct Agent（Execute 阶段） results = {} for task in sub_tasks: # 每个 sub_task 由独立的 ReAct 循环处理 results[task.id] = subagent_react_loop( task_description=task.description, tools=select_tools_for_domain(task.domain), max_iterations=8 ) # Step 3: 汇总 + 验证 report = assemble_dd_report(results) report["completeness_score"] = check_completeness(report) # 83% 预填率的来源 return report def subagent_react_loop(task_description: str, tools: list, max_iterations: int): """内层：纯 ReAct 循环（与 FXAgent 同构但更复杂）""" messages = [{"role": "user", "content": task_description}] for i in range(max_iterations): resp = client.messages.create( model="claude-sonnet-4-20250514", messages=messages, tools=tools, max_tokens=1024 ) if resp.stop_reason == "end_turn": return {"fields": parse_fields(resp.content[0].text), "iterations": i+1} # 执行工具并追加 observation for block in [b for b in resp.content if b.type == "tool_use"]: result = dispatch_tool_execution(block.name, block.input) messages.append({"role": "assistant", "content": [block]}) messages.append({"role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": json.dumps(result, ensure_ascii=False) }]}) return {"error": "达到最大迭代次数", "partial": messages}
架构洞察

注意 DDAgent 的同构性——外层 Dispatcher 和内层 SubAgent 使用完全相同的底层循环模式，区别只在：

  • 外层不需要 tools（纯规划），内层需要 tools（数据采集）
  • 外层输出是 task list，内层输出是结构化字段
  • 两层可以共享同一个 react_loop() 基础函数，通过参数控制行为

5.3 Eval Agent：用 Agent Loop 评测 Agent Loop

Eval Agent 是一个元 Agent——它的任务是评测其他 Agent/Skill 资产的质量：

def eval_agent_loop(target_agent_name: str, test_cases: list) -> dict: """ Eval Agent = 元循环（Meta-loop） 它本身就是一个 ReAct Agent，只不过它的"工具"是被测 Agent 和评测脚本。 """ eval_results = {"L1_behavior": [], "L2_routing": [], "L3_knowledge": []} for case in test_cases: === Eval Agent 自己的 ReAct 循环 === messages = [{"role": "user", "content": f"评测 {target_agent_name} 在以下测试用例上的表现: "{case}}] --- Thought: 决定用什么评测工具 --- --- Action: 调用被测 Agent 并收集其循环日志 --- agent_output = run_target_agent(case.input) messages.append({"role": "assistant", "content": "已收集被测 Agent 输出，开始分析..."}) messages.append({"role": "user", "content": f"被测输出: {agent_output}期望输出: {case.expected}'}) --- Observation: 获取被测输出后，继续思考评分 --- score_resp = client.messages.create( model="claude-sonnet-4-20250514", messages=messages, tools=EVAL_TOOLS, # compare_output / extract_facts / check_format ) --- 最终评分 --- scores = parse_eval_scores(score_resp.content[0].text) eval_results["L1_behavior"].append(scores.behavior) # 接受率 / 空填率 eval_results["L2_routing"].append(scores.routing) # 路由命中率 eval_results["L3_knowledge"].append(scores.knowledge) # 引用精度 # 汇总所有测试用例的评分 return { "target": target_agent_name, "L1_acceptance_rate": mean(eval_results["L1_behavior"]), "L2_route_accuracy": mean(eval_results["L2_routing"]), "L3_fact_precision": mean(eval_results["L3_knowledge"]), "overall_grade": compute_grade(eval_results) }
Eval Agent 的独特位置

Eval Agent 本身也是一个 ReAct Agent：调用被测Agent → 收集其循环日志 → 分析质量 → 输出评分。套娃，但是是有意义的套娃——它证明了 Agent Loop 是一个足够通用的抽象，连"评测 Agent"都可以用同一个模式实现。

本章核心收获
  1. Agent = LLM + 循环 + 工具，架构本身不复杂，复杂度在工具设计和工程守卫
  2. ReAct = Thought + Action + Observation 循环，是 2022 年提出、2026 年已成为行业默认标准的模式
  3. Function Calling 是三方契约：开发者定义 schema → LLM 决策调用 → Runtime 执行并回传结果
  4. stop_reason 决定循环生死：tool_use 继续，end_turn 结束，其他需异常处理
  5. Fitz 的 4 个 Agent 是 ReAct 的四种变体：DDAgent（多层编排）、BAAgent（数据飞轮）、FXAgent（短循环）、TRSAgent（长循环+容错）
  6. MCP 正在成为工具调用的 USB-C，但工具发现/认证/计费仍是开放问题
