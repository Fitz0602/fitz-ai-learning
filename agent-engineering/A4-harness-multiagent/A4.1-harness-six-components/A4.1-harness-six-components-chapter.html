① 是什么：Harness = 给野马套上缰绳

直觉类比

把大模型比作一匹力气惊人但方向感混乱的野马——它能跑，但不知道往哪跑、什么时候停。Harness 就是马具：缰绳控制方向、马鞍固定位置、马镫传递指令、眼罩限制视野。不是让马更聪明，而是让马的力量被可靠地使用。

1. 从"模型够强就行"到"系统决定上限"

2024 年之前，业界普遍的信念是：更好的模型 → 更好的 Agent。如果 Agent 表现不佳，等下一个模型。但 2026 年的实验数据颠覆了这个假设——

实验模型改变效果

OpenAI Codex 内部实验Codex（不变）重构 Harness3人 × 5月 = 百万行生产代码（零手写）
Claude Opus + 不同 Harness同一模型Harness 配置差异64.9% vs 57.6%（7pp 来自架构）
核心洞察

Agent = Model + Harness。同一模型在不同 Harness 下表现差距可达 13+ 个百分点——这超过了同期典型新模型发布带来的提升。不是模型不行，是围绕模型的系统没建好。

2. Harness 到底包含什么？

Harness 不是模型本身，也不是应用业务逻辑。它是模型和应用之间的一切：

Mitchell Hashimoto（HashiCorp 联合创始人）的指导原则精准概括了 Harness 工程的工作方式：

Mitchell Hashimoto 原则（2026.02）

"每当你发现 Agent 出错时，不要只是修复输出——要花时间设计一个工程化方案，使该 Agent 永远不会再犯同样的错误。"

这不是 Prompt Engineering（改一句话）。这是系统工程——构建环境、划定边界、建立反馈回路。

Takeaway

Harness 是模型和应用之间的工程化支撑系统，包含上下文、约束、工具、验证、记忆、反馈六个维度。它让"智能但不可控"的模型变成"智能且可靠"的 Agent。核心证据：仅优化 Harness（不换模型），准确率可提升 13+ 个百分点。

② 怎么实现：Fitz 六组件 vs 行业分解

直觉类比

把 Agent 想象成一位刚入职的实习生——Model 是她的智商和学历，Harness 是公司的入职体系：Goal Boundary=岗位描述（不该做的事别做）、Context=知识库和文档（该看什么）、Tools=工牌和系统权限（能用什么）、Scaffolding=SOP和检查清单（怎么做才对）、Feedback=周报和1on1（做对了没）、Memory=笔记和经验沉淀（下次做得更好）。

1. Fitz 原创六组件框架

在 A3.2 Memory 四层架构中，我们已理解记忆系统是 Harness 的一部分。现在将视野拉到全景——Fitz 基于对 DDAgent 工程实践的反思，提炼出六个正交组件：

2. 六组件详解

① Goal Boundary（目标边界）——定义 Agent "不该做什么"比"该做什么"更重要。

  • 意图建模：将用户模糊需求转化为可执行的 Agent 目标
  • 权限栅栏：明确哪些动作需要审批、哪些可自主执行
  • 范围控制：防止 Goal Drift（目标漂移）和 Scope Creep（范围蔓延）

DDAgent 实例：Dispatcher 只做路由不分诊，子 Agent 只管自己银行——这是典型的 Goal Boundary 设计。

② Context（上下文工程）——Agent 能看到什么决定了它能做好什么。

  • 信息注入时机和方式的工程化（→ A3.1 已详述）
  • 上下文文件的精简原则（AGENTS.md ≤ 60 行）
  • 滑动窗口 vs 摘要传递 vs 结构化工件交接

③ Tools（工具层）——Agent 能"动手"做什么。

  • 工具注册和 MCP 协议标准化（→ A1.2 已详述）
  • CLI 封装优先于自定义工具（模型训练数据中 CLI 用法丰富）
  • 工具作用域限制（文件系统隔离、API 权限控制）

④ Scaffolding（脚手架）——让 Agent 沿着"正确的路径"走，而不是在空旷中迷失。

  • SOP 和检查清单：Agent 执行前/后必须跑的验证步骤
  • 架构约束：通过 Linter、类型检查强制执行代码规范
  • 设计原则：约束解空间而非扩大它——更少的有效选项 = 更少的错误答案

⑤ Feedback（反馈闭环）——没有反馈就没有改进，没有 Gate 就没有质量。

  • 验证循环：Agent 每步操作后自动检查（测试套件、构建验证、截图对比）
  • 评估器（Evaluator）：Anthropic 三角色系统中的 Evaluator 角色
  • Gate 机制：DDAgent 的 auditor 只标不改——质量门槛，不是修改工具

⑥ Memory（记忆系统）——从"每次从零开始"到"越用越靠谱"。

  • 四层架构已在 A3.2 详述：主上下文 / 工作上下文 / 外部上下文 / 程序性记忆
  • 在 Harness 框架中，Memory 是跨会话持续进化的引擎
  • 进度记录：长时间任务的断点恢复和上下文重建

Fitz 六组件与行业分解的关键差异：Goal Boundary 和 Memory 被独立为顶层组件。OpenAI 把目标归入"架构约束"、把记忆归入"生命周期管理"——但在 DDAgent 实践中，目标边界（谁该做什么）和记忆（跨会话状态）是错误最集中的地方，值得独立关注。Thoughtworks 的 2×2 矩阵（guides/sensors × computational/inferential）更偏理论抽象，Fitz 框架更偏工程实操。

Takeaway

六组件框架的核心价值是正交性：每个组件可以独立迭代。LangChain 实验证明，仅优化 Context（AGENTS.md）和 Feedback（自我验证循环），就能带来 +13.7pp 的提升。不需要同时优化六个——找到瓶颈组件，集中火力。

③ 为什么：无状态函数 → 可靠系统的鸿沟

直觉类比

模型就像一个天才临时工——每次来上班都失忆，不知道公司做什么、自己负责什么、之前做过什么、什么算做好。Harness 就是让临时工变成正式员工的"入职体系"：岗位描述（Goal）、知识库（Context）、工牌（Tools）、SOP（Scaffolding）、质检（Feedback）、笔记（Memory）。天才不缺，缺的是让天才稳定发挥的系统。

1. 第一性原理：模型是纯函数，Agent 需要状态机

从数学角度看，大语言模型的本质是：

$$f: \text{Tokens}_{\text{in}} \rightarrow \text{Tokens}_{\text{out}}$$

这是一个无状态纯函数——同样的输入永远产生同样的输出。但 Agent 需要的是：

$$A: (\text{Goal}, \text{State}_t, \text{Environment}) \rightarrow (\text{Action}_t, \text{State}_{t+1})$$

这是一个有状态决策系统——需要跟踪目标、维护状态、感知环境。模型和 Agent 之间的鸿沟，正是 Harness 要填补的：

2. 设计取舍：为什么 Harness 比模型更重要

理由一：模型趋同，Harness 分化

2026 年 2-3 月，GPT-5.4、Gemini 3.1 Ultra、Grok 4.20 接连发布，顶级模型间的能力差距已压缩到周级别。模型正在成为商品（commodity），而 Harness 是可设计的差异化壁垒——任何有纪律的团队都能构建。

理由二：错误复利效应

Agent 在 5 步轨迹中，每步 5% 的错误率会复利为：

$$P(\text{整体成功}) = (1 - 0.05)^5 \approx 77.4\%$$

10 步轨迹则降至 60%。单步看似可靠，多步后雪崩。Harness 的 Feedback 组件在每个步骤插入验证，把复利链打断：

$$P(\text{单步成功 | Gate}) = 1 - P(\text{错误}) \times P(\text{未检出})$$

如果 Gate 能检出 90% 的错误，单步失败率从 5% 降至 0.5%，10 步成功率从 60% 升至 95%。

理由三：模型不可控，Harness 可控

模型的权重你改不了，但 Harness 的每个组件你都能改。Mitchell Hashimoto 的原则——"让 Agent 永远不再犯同样的错误"——只有通过 Harness 工程才能实现。你不能训练模型不犯某个错，但你可以加一条规则、一个检查清单、一个中间件来阻止它。

3. 上下文腐烂：长时运行 Agent 的头号杀手

Agent 在第 100 次工具调用后，是否还能遵循原始指令？这就是上下文腐烂（Context Rot）问题：

  • 每次调用消耗上下文窗口，原始目标被压缩或替换
  • 中间结果堆积，无关细节污染上下文
  • Agent 开始重复自己（Loop Drift）或偏离目标（Goal Drift）

Harness 的三个对策：

问题Harness 方案组件
上下文溢出摘要传递 + 上下文重置Context + Memory
目标遗忘定期重新锚定原始目标Goal Boundary
循环重复循环检测中间件Feedback
Takeaway

Harness 的本质是将无状态纯函数转化为有状态可靠系统的工程桥梁。它比模型更重要的三个原因：模型趋同而 Harness 分化、错误在多步中复利、模型不可控但 Harness 可控。上下文腐烂是长时运行 Agent 的头号问题，需要 Context + Goal Boundary + Feedback 三组件协同应对。

关键发现

⑤ 与产品连接：DDAgent Harness 逐组件审视

直觉类比

DDAgent 就像一个跨境汇款专柜——Dispatcher 是大堂经理（判断客户需求路由到哪个窗口），子Agent 是各银行专柜的柜员（按SOP处理），Auditor 是后台质检员（只标错不改错）。Fitz 六组件框架就是审视这个专柜体系的设计图纸——每个组件是否到位？哪些是瓶颈？

3. 具体改进路径

Memory 改进（2→4 星）：

1
引入案例库：将历史处理成功的汇款案例结构化存储，子 Agent 遇到相似场景时自动检索类比（→ A3.2 外部上下文层）
2
进度记录持久化：长时间尽调任务的断点保存，会话中断后可恢复（→ Anthropic 基于Git的进度追踪模式）
3
程序性记忆：记录"哪种银行+哪种汇款类型"的最优处理路径，下次自动复用

Scaffolding 改进（3→4 星）：

1
显式检查清单：子 Agent 在提交结果前，必须过一遍"必查项"（收款人名一致性、金额范围、合规标记）
2
结构化输出约束：用 JSON Schema 强制输出格式，而非自由文本（→ "约束解空间"原则）
3
自我验证循环：提交前 Agent 自行运行一次验证（金额是否匹配、字段是否完整）

警惕

不要陷入"全组件同时升级"的陷阱。LangChain 实验证明，仅优化 2-3 个组件就能带来巨大提升。优先级：Memory → Scaffolding → Context。Goal Boundary 和 Feedback 已经做得不错，维持即可。

Takeaway

用 Fitz 六组件框架审视 DDAgent，发现 Memory（2星）和 Scaffolding（3星）是最大瓶颈。改进路径清晰：Memory 引入案例库+进度持久化+程序性记忆；Scaffolding 增加检查清单+结构化输出+自我验证。核心原则：找到瓶颈组件，集中火力，而非全组件均衡发力。
