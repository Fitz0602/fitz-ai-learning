§1 是什么：Planning 的直觉

PM 直觉类比：徒步者 vs 战略家

想象两个人在穿越一片从未涉足的原始森林。

徒步者 A：每到一个岔路口，停下来观察地面脚印、听风声、闻气味，然后选一条路继续走。走到死胡同就退回来，换另一条。这就是 ReAct——"推理一步，行动一步，再推理，再行动"。高效吗？对短途旅行足够了。

战略家 B：出发前先爬上最高的一棵树，俯瞰整个森林地形，画出一张路线图："先往东北方向走 2 公里到河边，然后沿河向东 3 公里找到木桥，过桥后往南……"路上每完成一段，他会重新评估进展、调整后续路线。这就是 Plan-Act-Reflect——"先有全局蓝图，再分段执行，持续校准"。

1.1 从 A1.1 的 ReAct 到这里：我们缺了什么？

A1.1 章节详细讲解了 ReAct 循环（Thought → Action → Observation），它是 Agent 的基础执行引擎。但当你把 ReAct 应用到真正的复杂任务时，会撞上一堵墙：

⚠️ ReAct 在复杂任务中的三大致命缺陷
  1. 短视决策：每一步只基于当前 Observation 做选择，没有全局视角。就像下围棋只看下一步——能吃子，但赢不了棋局
  2. 重复试错：同一种错误模式可能反复出现（比如反复用错误参数调用同一个 API），因为没有记忆和反思机制
  3. 无法分解：面对"帮我做一次完整的银行尽调报告"这种多步骤任务，ReAct 不知道该拆成哪些子任务、用什么顺序、每个子任务的产出物是什么

这就是为什么我们需要 Plan-Act-Reflect——它不是要替代 ReAct，而是给 ReAct 加上一层战略指挥层。

1.2 Plan-Act-Reflect 三阶段的本质

阶段做什么输出类比
Plan将模糊用户指令分解为清晰可执行的步骤列表初始路线图（非一成不变）项目经理写 WBS（工作分解结构）
Act调用工具执行具体步骤每步的中间结果开发团队写代码/跑测试
Reflect评估正确性、检查进展、发现问题、更新策略评估报告 + 更新后的计划Sprint Review / 代码审查
💡 核心洞察

反思（Reflect）是区分"脚本执行器"与"智能体"的分水岭。

一个没有 Reflect 的 Agent = 一段 if-else 脚本，只是恰好由 LLM 驱动而已。它只能沿着预设路径机械地执行。而有 Reflect 的 Agent 能在执行过程中自我诊断——"这步结果对不对？跟预期差多少？是不是我的方法有问题？要不要换一个方案？"

这个能力让 Agent 从"工具使用者"进化为"问题解决者"。

§2 怎么实现：Plan-Act-Reflect 三阶段循环

2.1 Plan 阶段：任务分解算法

Plan 阶段的目标是将用户的高层意图转化为可执行步骤列表。这不是简单的文本拆分，而是需要结构化的推理过程：

📌 DDAgent 的 Plan Prompt（伪代码）
# plan_prompt.py  —  DDAgent 的规划阶段 Prompt
PLANNING_SYSTEM_PROMPT = """你是一个尽职调查任务规划器。
你的输入是一个用户请求，输出是一份结构化的执行计划。

## 输入
用户请求：{user_request}

## 输出格式
返回 JSON 数组，每个元素代表一个执行步骤：
[
  {{
    "step_id": 1,
    "action": "search_enterprise",
    "description": "搜索企业基础工商信息",
    "input": {{"company_name": "{extracted_name}"}},
    "expected_output": "企业全称、统一社会信用代码、注册资本等",
    "depends_on": [],           // 无前置依赖
    "can_parallel": false
  }},
  {{
    "step_id": 2,
    "action": "query_risk_tags",
    "description": "查询风险标签集合",
    "input": {{"company_id": "$step1.company_id"}},  // 引用前一步输出
    "expected_output": "诉讼/被执行/经营异常等标签列表",
    "depends_on": [1],
    "can_parallel": false
  }},
  // ... 后续步骤
]

## 规划原则
1. 每个步骤必须对应一个可调用的 Tool
2. 步骤之间通过 $stepN.xxx 引用前序输出的字段
3. 标注 depends_on 以便并行优化
4. 如果某步可能失败，标注 fallback_plan
"""

# 关键设计点：
# - 结构化输出（JSON）→ 可被程序解析和调度
# - 依赖关系（depends_on）→ 支持并行化
# - 变量引用（$stepN）→ 步骤间数据流显式化
# - fallback_plan → 预设容错路径

2.2 Act 阶段：工具调度执行

Act 阶段相对直观：按照 Plan 生成的步骤列表，依次（或并行）调用对应的工具。核心挑战不在于"调用"，而在于"处理异常和传递上下文"。

1
取当前步骤 → 从 Plan 中取出下一个待执行的 step（考虑 depends_on 是否满足）
2
解析输入 → 将 $stepN 变量引用替换为实际值（如 Step 2 的 company_id 来自 Step 1 的输出）
3
调用工具 → 执行 Tool Call（如 search_enterprise(name="腾讯控股")）
4
捕获结果 → 记录返回值、耗时、是否异常（超时/错误码/空结果）
5
传递上下文 → 将结果注入下一步的输入变量池，进入下一轮或进入 Reflect

2.3 Reflect 阶段：两种反思模式

这是整个框架中最关键也最灵活的阶段。什么时候反思、反思多深，直接决定了 Agent 的效率和准确率之间的权衡。

维度逐步反射 Mode B全局反射 Mode A
触发时机每执行完一步后立即反思全部步骤执行完后一次性反思
纠错及时性高——问题立刻发现立刻修低——错误可能在中间累积
计算成本高——每步都调用 LLM 做 Reflect低——只调用一次 Reflect
适用场景长链路任务、易出错场景、高价值操作短任务、低风险操作、追求速度
典型例子DDAgent 尽调（每步数据质量决定后续）KBAgent 主题挖掘（批量生成后统一审查）
风险过度反思导致执行效率下降早期小错误被放大成大问题
✅ 实践经验法则
  • 默认用 Mode A（全局反射）——大多数任务不需要每步都反思，一次复盘就够了
  • 关键节点强制 Mode B——涉及资金操作、数据写入、不可逆动作时，务必逐步反射
  • 混合模式最佳：大部分步骤用全局反思 + 关键步骤插入手动 Reflect checkpoint

§3 为什么：第一性原理分析

3.1 为什么规划比"走一步看一步"更优？

这个问题可以归结为一个经典的计算机科学问题：搜索空间裁剪（Search Space Pruning）。

假设一个任务需要执行 $k$ 个步骤，每一步平均有 $b$ 种可选动作（分支因子）。那么：

  • 无规划（纯 ReAct 盲搜）：搜索树大小为 $O(b^k)$ ——指数爆炸
  • 有规划（Plan 先约束再执行）：Plan 阶段将有效搜索空间压缩为线性路径 $O(k \cdot c)$，其中 $c$ 是每步的平均候选数（通常 $c \ll b$）
📐 一个具体数字例子

以 DDAgent 尽调为例：完整流程需要 5 个主要步骤，如果每步平均有 8 种可能的 Tool/参数组合：

  • 纯 ReAct：$8^5 = 32,768$ 种可能的执行路径需要探索
  • Plan-Act-Reflect：Plan 阶段锁定为 1 条最优路径（~5 步），每步只需在 ~2 个候选中验证（Reflect 微调），总探索量 $\approx 5 \times 2 = 10$

搜索量缩小了约 3,000 倍——这就是规划的威力。而且随着任务复杂度增加（$k$ 变大），这个倍数呈指数增长。

3.2 错误早发现（Fail Fast）原理

除了搜索空间裁剪，规划的第二个核心价值是 错误早发现。

在没有 Plan 的情况下，Agent 可能执行了 4 个步骤后才在第 5 步发现"第一步的参数就错了"。这意味着前面 3 步的工作全部浪费。

而有了 Reflect 机制：

R1
Plan 时就能发现逻辑矛盾（比如"先查风险标签但还没拿到 company_id"）
R2
Step 1 Reflect 时发现返回的企业名称不匹配，立即修正搜索关键词，避免后续全部跑偏
R3
Step 2 Reflect 时发现风险标签 API 返回空结果，立即切换到备用数据源而不是傻等
💡 反思的经济学

每次 Reflect 调用的成本 ≈ 一次 LLM inference（~$0.01-$0.03）。但如果不在 Step 1 发现错误而等到最后才发现，浪费的是 4 次 Tool 调用 + 4 次 LLM 推理 + 全部上下文重建的成本（可能是 $0.5-$2.0）。

ROI = 反思节省的错误传播成本 ÷ 反思本身的成本。对于长链路任务，这个 ROI 通常在 10x-50x 之间。

4.1 技术演进时间线

4.2 关键研究逐一解读

🔬 Reflexion（Shinn et al., 2023）：语言强化学习的突破

Reflexion 是第一个系统性地将"反思"作为独立模块提出的工作。它的核心创新：

  • Verbal Reinforcement Learning：不用标量奖励信号（如 +1/-1），而是用自然语言形式的反馈（如"你在第 3 步用了错误的 API 参数格式"）
  • 持久记忆：将反思结论写入长期记忆（向量数据库），下次遇到类似情境时自动检索历史教训
  • 自我纠正循环：Agent 失败 → 反思原因 → 生成改进策略 → 重试 → 直到成功或达到最大轮次

效果：在 ALFWorld（交互式家居环境）上的成功率从基线的 37% 提升到 97%。在 HotPotQA（多跳问答）上从 53% 提升到 91%。

🔬 Pre-Act：执行前的深度推理

Pre-Act 的核心思想是：不要在执行过程中才思考，先把每一步都想清楚再动手。

  • 执行前生成完整的多步计划 + 每步的详细推理链（为什么选这个工具、预期什么结果）
  • 每步执行后进行迭代修正——比较实际结果与预期，偏差超过阈值时自动调整
  • Action Recall 提升 ~70%：模型在后续步骤中能准确回忆之前做了什么、结果如何

🔬 SPIRAL（IBM, AAAI 2026）：符号化规划的新高度

这是目前最先进的 Plan-Act-Reflect 框架之一，来自 IBM Research 并发表于 AAAI 2026。它引入了三个专业化角色：

🔍 SPIRAL vs 传统 Plan-Act-Reflect 的区别

传统框架中，Plan/Act/Reflect 都由同一个 LLM承担。而 SPIRAL 将它们拆分为三个专门化角色，每个角色有自己的 System Prompt 和专注领域：

  • Planner = 创意发散者（像产品经理 brainstorming）
  • Simulator = 务实检验者（像 QA 工程师做可行性测试）
  • Critic = 严苛评审者（像 Tech Lead 做 code review）

这种角色分工避免了"既是运动员又是裁判"的认知偏差，显著提升了规划质量和反思深度。

🧠 MAP（Modular Agentic Planner）：脑启发式架构

MAP 将人脑前额叶皮层的功能映射为 6 个独立模块：

模块功能对应大脑区域
任务分解器将高层目标拆解为子目标背外侧前额叶（dlPFC）
行动者执行具体动作运动皮层
监控器跟踪进度、检测偏离前扣带皮层（ACC）
预测器预测下一步的可能后果眶额皮层（OFC）
评估器评估当前状态的价值腹内侧前额叶（vmPFC）
编排器协调各模块间的信息流前额叶网络整合区

4.3 企业级五种工作流（Anthropic 分享）

Anthropic 在其官方文档中总结了企业级 Agent 应用的五种基本工作流模式。其中第 4 种（Orchestrator-workers）最接近 Plan-Act-Reflect 的工程实践：

#工作流描述对应本章概念
1链式提示 (Prompt Chaining)上一个 prompt 的输出作为下一个的输入，串行流水线简化的 Act 阶段（无 Reflect）
2路由系统 (Routing)分类用户意图后路由到专门的子流程Plan 阶段的"意图→子任务"映射
3并行化 (Parallelization)同时运行多个独立任务，汇总结果Plan 阶段标注 can_parallel 的步骤并发执行
4协调器编排 (Orchestrator-Workers)中央协调器分配任务给多个 Worker，收集并整合结果最接近 Plan-Act-Reflect：Coordinator=Plan+Reflect, Workers=Act
5评估器优化器 (Evaluator-Optimizer)生成初稿 → 评估器打分 → 优化器根据评分改进 → 迭代直到达标Reflect + Plan 修正的循环变体
⚠️ 不要过度设计

五种工作流中，80% 的实际需求用 #1（链式提示）+ #2（路由）就能解决。只有当任务真正需要跨多个 Worker 协作时才上 Orchestrator。过早引入复杂架构会导致调试困难、延迟增加、成本上升。

5.3 KBAgent 的反思闭环

你的 KBAgent（知识库生产 Agent）提供了另一种 P-A-R 模式的实例：

  • Plan：根据主题类型决定走"标准流程"还是"深度挖掘"（depth 参数控制）
  • Act：执行三段式流水线（Topic Mining → HQA Extraction → Topic Linking）
  • Reflect：
    • HQA 质量门禁：每个 HQA 必须是真问题 + 有明确答案 + 可独立存在
    • 空泛内容过滤：禁止"请参考官方文档"之类的废话
    • 关联完整性：新主题至少建立 3 条关联边

成果：截至 2026-05，KBAgent 已产出 86 条主题 + 443 条 HQA，且质量一致性好于人工编写（因为 Reflect 门禁比人类审查更严格一致）。

💡 A2.2 核心结论
  1. Plan-Act-Reflect 不是 ReAct 的替代品，而是它的战略升级：ReAct 负责"战术执行"（单步决策），P-A-R 负责"战略指挥"（全局规划+纠偏）
  2. Reflect 是分水岭：没有 Reflect 的 Agent 只是高级脚本；有了 Reflect 才成为真正的"智能体"
  3. 两种反思模式各有场景：默认全局反思（低成本），关键步骤逐步反思（高保障）
  4. 研究前沿已走向角色分工：从单一 LLM 做 P-A-R → SPIRAL 的 Planner/Simulator/Critic 三角协作
  5. 你的 DDAgent 已经在实践中验证了这个范式：83%预填 / 95%准确 / 100%路由的数据就是最好的证据
