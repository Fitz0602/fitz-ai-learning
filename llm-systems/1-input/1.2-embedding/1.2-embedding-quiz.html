关于 Token Embedding，以下哪项描述最准确？
A. Embedding 是一个查找表（Lookup Table），把 token ID 映射到工程师手工设计的高维向量
B. Embedding 把 token ID 映射到高维稠密向量，向量由预训练自动学习得到；语义相近的 token 在向量空间中距离更近
C. Embedding 是 Tokenizer 的另一个名字，两者可以互换使用
D. Embedding 矩阵的形状是 [隐藏维度, 序列长度]

Q2 · 判断应用
以下关于 Embedding 的说法，哪一项是错误的？
A. Embedding 矩阵形状是 [词表大小, 隐藏维度]，词表大小直接决定 Embedding 参数量
B. 不同模型训练出的 Embedding 向量互不相通——GPT-4 的向量在 DeepSeek 的空间里没有意义
C. Embedding 空间里的向量运算有意义：如 vec("国王") - vec("男人") + vec("女人") ≈ vec("女王")
D. 由于 Embedding 能捕获语义，RAG 系统可以用 Embedding 相似度来完成精确的实时数字查询（如今日汇率）

Q3 · 概念辨析
Embedding 矩阵预训练前是随机噪声，预训练后"美元"和"日元"的向量自然相邻。这是怎么发生的？
A. 工程师在预训练时手动标注了"美元"和"日元"语义相近，模型据此调整向量
B. 预训练任务（下一个 token 预测）产生梯度信号，"美元"和"日元"在大量语料里出现在极相似的上下文中，梯度方向相似，反向传播后它们的向量自然靠近
C. 模型使用 Word2Vec 算法预先计算了词语相似度，再初始化 Embedding 矩阵
D. Embedding 矩阵用余弦相似度公式初始化，让语言学上相关的词天然接近

Q4 · 判断应用
大模型的 Embedding 层和 Unembedding 层（将隐藏向量投影回词表）有时会共享权重（Weight Tying）。以下关于 Weight Tying 的说法，哪项最准确？
A. 所有现代大模型都强制要求 Weight Tying，这是行业强制标准
B. Weight Tying 的核心逻辑是：输入端"理解 token"和输出端"生成 token"用到的语义表示应该相同，共享参数还能减少参数量
C. Weight Tying 会导致模型无法区分输入和输出，实践中效果更差
D. GPT-3 之后，所有规模的大模型都默认使用 Weight Tying

Q5 · 概念辨析
为什么大模型用 7168 维稠密向量（DeepSeek-V3），而不用 128000 维 One-Hot 编码？以下哪项抓住了根本原因？
A. One-Hot 占用显存太多，纯粹是工程性能问题
B. 大模型只能处理浮点数，无法处理 0/1 整数
C. One-Hot 让所有 token 两两正交（余弦距离均为 0），无法表达"美元"和"日元"比"美元"和"番茄"更相关——丢失了语义结构，是表达力问题而非性能问题
D. One-Hot 是早期废弃技术，现代 NLP 没人用，原因已不重要

Q6 · 判断应用多选
以下关于 Embedding 维度设计的说法，哪些是正确的？（选所有适用的选项）
A. 隐藏维度越大，理论上模型表达能力越强，但计算量和参数量也随之增加
B. GPT-4 使用约 12,288 维，DeepSeek-V3 使用 7,168 维，这种差异反映了不同架构下性能与效率的取舍
C. Embedding 维度越高，模型的词表大小必须成比例增加，否则会导致欠拟合
D. 在 RAG 场景中，生成模型的 Embedding 维度与检索用的专用 Embedding 模型维度没有直接关系——两者是独立系统

④ 演进格局
Q7 · 概念辨析
以下关于 Embedding 技术演进的描述，哪项最准确？
A. Word2Vec 每个词有一个固定向量（静态 embedding），无法区分"bank=银行"和"bank=河岸"；BERT 等上下文 embedding 解决了这个多义词问题
B. BERT 和 GPT 的 embedding 实现完全相同，可以互相替换用于生成任务
C. 现代 RAG 系统直接用生成大模型（如 GPT-4）的内部 embedding 来做检索，不需要专用 embedding 模型
D. Matryoshka Embedding（MRL）要求截取后必须重新训练，无法直接使用截短的子向量
参考：④ 演进格局
Q8 · 判断应用多选
以下关于 Matryoshka Representation Learning（MRL，套娃 embedding）的说法，哪些是正确的？（选所有适用的选项）
A. MRL 允许用同一个模型的前 256 维、512 维、1024 维子向量分别完成检索，无需重新训练
B. OpenAI text-embedding-3 和 Nomic Embed 都支持 MRL 截断功能，是行业共识
C. MRL 截断后语义完全等价于全维度，检索精度不会有任何损失
D. MRL 在存储受限的场景（如移动端、边缘计算）有显著优势，可以用更少的存储换取可接受的精度损失
参考：④ 演进格局

Q9 · 概念辨析
KBA 知识库系统使用 RAG（检索增强生成）架构，用 Embedding 相似度召回文档片段。以下哪项最能说明"专用 embedding 模型 + 生成模型解耦"是最佳实践？
A. 因为生成模型的 API 太贵，分开用可以节省成本
B. 专用 embedding 模型（如 BGE-M3、Voyage-3）针对检索任务专门优化了向量空间，比直接用生成模型的内部 embedding 检索精度更高；同时两者解耦可以独立升级
C. 生成模型的 embedding 不是向量格式，无法用于检索
D. 专用 embedding 模型的向量维度更低，存储更省，所以更好

Q10 · 判断应用
FxAgent 用户问"今天美元兑日元汇率多少"，如果完全依赖 Embedding RAG 检索知识库，最可能出现什么问题？
A. "今天"和"昨天"在 embedding 空间非常接近，RAG 可能召回昨天或上周的汇率数据，而 embedding 无法区分时效性——实时数字查询应走结构化 API 而非 RAG
B. 汇率数字（如 157.32）无法被 tokenizer 处理，所以 RAG 直接报错
C. Embedding 无法处理中文，导致"美元兑日元"的语义理解失败
D. RAG 召回速度太慢，无法满足实时查询需求，这是主要问题
