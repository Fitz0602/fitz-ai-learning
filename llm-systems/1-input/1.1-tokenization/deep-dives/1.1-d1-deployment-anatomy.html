大模型部署解剖：以 DeepSeek-V3 (671B) 为例

大模型 = 词表 + 模型权重 + 配置 + tokenizer 程序 · 不到 10 类文件就是模型的全部
▎核心结论
一个 1.3 TB 的"庞然大物"，本质上只由 4 类文件构成。其中最关键的不是最大的——词表（tokenizer.json）只有 8 MB，但定义了模型"听得懂的语言"。词表与权重是硬绑定的，改一个 token 的 ID 模型立刻崩溃。

1. 文件清单总览（DeepSeek-V3 真实结构）

2. 4 类文件逐个拆开

🟣 类 1：词表 — tokenizer.json（8 MB）

BPE 词表的物理形态。打开它就是一份 JSON：

{
  "model": {
    "type": "BPE",
    "vocab": {
      "<|begin▁of▁sentence|>": 0,
      " the": 262,
      " of": 286,
      "我": 47100,
      "美元": 92831,
      "经济": 100208
    },
    "merges": [
      ["t", "h"],
      ["th", "e"],
      [" ", "t"],
      [" t", "he"]
    ]
  }
}
字段作用
vocab词表本体：字符串↔ID 的双向字典
mergesBPE 训练期所有合并规则，按顺序排列
pre_tokenizer预处理（如数字按 3 位切）

DeepSeek-V3 词表 129,280 个 token；GPT-4o 的 o200k_base 是 200K。文件本身是 UTF-8 文本，你可以直接用文本编辑器打开。

🟠 类 2：模型权重 — model-*.safetensors（1.3 TB）

分成 163 片不是技术挑战，是工程便利（断点续传、多机并行加载）。每片大约 8 GB。

里面是一个巨大的字典，存放每一层的参数：

model.embed_tokens.weight              [129280, 7168]   ← 词嵌入矩阵
model.layers.0.self_attn.q_proj.weight [7168, 7168]
model.layers.0.self_attn.k_proj.weight [7168, 1024]
model.layers.0.self_attn.v_proj.weight [7168, 1024]
model.layers.0.mlp.gate_proj.weight    [...]
... 重复 61 层 ...
model.norm.weight                      [7168]
lm_head.weight                         [129280, 7168]   ← 输出层
▎硬绑定关系
embed_tokens 形状 [129280, 7168] = 词表大小 × 隐藏维度。

每一行向量对应词表里某个具体 token ID。如果你改 tokenizer.json 里"美元"的 ID 从 92831→99999，模型立刻崩溃——它去 embedding 第 99999 行查向量，但那行训练时存的是别的 token 的语义。

这就是为什么"换 tokenizer = 全模型重训"。

不同精度下的体积对比

精度每参数字节总大小使用场景
FP324~2.7 TB训练（罕见，多用 BF16）
BF16/FP162~1.3 TB主流推理 ✓
INT81~671 GB云推理常用
INT40.5~340 GB本地部署

🔵 类 3：配置 — config.json（4 KB）

没几 KB，决定了模型的全部架构。这是模型的"基因身份证"：

{
  "model_type": "deepseek_v3",
  "vocab_size": 129280,                ← 必须等于 tokenizer 词表大小
  "hidden_size": 7168,                 ← 每个 token 向量维度
  "num_hidden_layers": 61,             ← 61 层 Transformer
  "num_attention_heads": 128,          ← 多头注意力的"头"数
  "intermediate_size": 18432,          ← FFN 中间维度
  "max_position_embeddings": 163840,   ← 最大上下文 16 万 token
  "rope_theta": 10000,                 ← 位置编码参数（W3 学）
  "torch_dtype": "bfloat16",
  "n_routed_experts": 256,             ← MoE 专家数
  "n_active_experts": 8                ← 每次激活几个
}

理论上拿着这个 config + 框架代码，就能搭出一个空壳模型——只是没训练过，输出全是噪声。

4. 加载与推理的完整生命周期

阶段用到哪些文件动作
启动config.json读架构参数，初始化空壳模型
加载词表tokenizer.json + tokenizer_config.json在内存里建 token↔ID 双向哈希表
加载权重model.safetensors.index.json + model-*.safetensors × 163按片读权重到 GPU 显存
推理（每次请求）tokenizer.json + 全部权重 + generation_config.json切词→embedding→61 层 Transformer→采样→反查
关闭—释放显存

6. 串到你的产品视角

▎与跨境支付 / DDAgent / KBA 的连接
  1. 模型私有化部署评估：当合规要求模型不出公司边界时，知道 1.3TB / 340GB 的具体体积差距，能秒答硬件成本
  2. 解释为什么 fine-tune 不动 tokenizer：你给团队做培训时这是关键概念——微调只在已有词表的语义空间内调整，不会让模型"学会新词"
  3. 专有名词的根本困境：FxSkill/网联清算/离境退税这些词，无论你怎么 fine-tune 都不会得到独立 token——必须靠 system prompt 注入或 RAG 召回
  4. 量化选型决策依据：Knot 平台选模型时，BF16 vs INT8 vs INT4 的取舍现在有了底层认知
  5. config.json 是论文索引：以后读 LLM 论文，直接翻附录的 config，能秒懂模型规模和架构选择

7. 一个让你彻底记住的画面

▎Mental Model
把大模型想象成一本超大型的书：

📖 tokenizer.json = 目录 + 字典（8 MB · 告诉你每个字怎么读、什么编号）
🧠 model.safetensors = 正文（1.3 TB · 全部知识储备）
🏗️ config.json = 装订规格（4 KB · 多少页、多大开本）
🎬 辅助文件 = 使用说明书（<1 MB · 怎么用这本书）

这本书的奇特之处：字典只有 8MB，正文 1.3TB，但字典定义了正文里每个字的意义。改字典 = 把正文里所有字的含义全部打乱。
