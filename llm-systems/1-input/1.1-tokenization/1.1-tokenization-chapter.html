▎为什么从这里开始
你做了4个生产级Agent，但有没有想过：用户输入"我想换100美元到日元"这一句话，模型真正"看到"的是什么？是 13 个汉字+数字+字母吗？不是。它看到的是一串数字 ID：[31476, 88229, 9554, ...]。

这串数字怎么来的？为什么OpenAI按token计费，1个汉字往往要花2-3个token，但1个英文单词可能只算1个？为什么有些模型对中文表现差？答案都在Tokenizer这一层。

这是LLM最底层、最容易被产品经理忽略、却又直接影响成本与效果的一环。学完今天你将彻底理解：模型"识字"的方式，和人类完全不同。

① 是什么 — 模型不识字，只识ID

大模型本质是一个矩阵乘法机器。它不能直接处理文本——所有输入必须先变成数字索引。这个翻译过程就叫 Tokenization（分词）。

"换100美元" → Tokenizer → [换][100][美][元] → [2391, 1633, 9876, 3210]
原文 → 切成 token 序列 → 每个 token 查表得到整数 ID

这里有几个关键概念，先把术语对齐：

Token（词元）
模型处理的原子单位。可能是 1个字、半个词、1个标点、甚至1个空格——长度不固定，由算法从训练数据中统计得出。
Vocabulary（词表）
所有可能 token 的集合，每个 token 有唯一整数 ID。词表大小 = embedding 矩阵的行数——这是理解后续 scaling 的关键。
Tokenizer
把"原始文本 ↔ token ID 序列"双向翻译的确定性程序。同一份代码 + 同一份数据 = 任何时候切出来的结果完全一样。
Embedding（嵌入）
把 token ID 转成一个高维稠密向量（如 4096 维），让模型可以做矩阵运算。是 Tokenizer 的下一步，下一章讲。

第一性原理：Tokenization 本质上是一个有损压缩编码问题——在有限词表预算下，如何把无限可能的文本映射为有限集合中的元素序列，同时最大化信息保留率。所有 tokenizer 变种都是对这个问题的不同近似解。

📂 各阶段详情

阶段 ① · NFC Unicode 归一化
这一步干啥

把"长得不一样但意思一样"的字符统一成一种标准写法。本例的英文+数字不涉及 Unicode 多形态，所以输入输出一致。

触发场景示例：café（重音符可拆/合）、全角半角标点、韩文组合字符等。

💡 比喻：就像快递员收件前先把"广东省·深圳"和"广东深圳"都改写成"广东省深圳市"——后续处理只需要认一种格式。

阶段 ② · 正则预分词（最关键的一步）
这一步干啥

用正则规则把整句切成一块块大的"半成品"（叫 pre-token），后面 BPE 只能在每块内部玩，跨不过去。

本例切分结果（8 个 pre-token）：

I want to exchange 123 45 dollars

注意 "12345" 被拆成 123 + 45——这是正则切的，不是 BPE 干的（很多人搞错的关键点）。

💡 比喻：就像拆快递先按"形状大类"分箱——长方形进 A 区、圆柱形进 B 区。后面拣货员（BPE）只能在自己负责的箱子里挑，不能跨箱。

阶段 ③ · UTF-8 字节化
这一步干啥

计算机不认识"字母"或"汉字"，只认识 0-255 的字节。把每个 pre-token 翻译成字节序列。这一步纯翻译，不做任何合并/拆分判断。

本例 8 个 pre-token 的字节序列：

I[73]1 byte
want[32, 119, 97, 110, 116]5 bytes
to[32, 116, 111]3 bytes
exchange[32, 101, 120, 99, 104, 97, 110, 103, 101]9 bytes

非 ASCII 字符对照（字节数固定）：

"美"[0xE7, 0xBE, 0x8E]3 bytes（中文恒 3 字节）

💡 比喻：就像翻译——把每个英文字母 / 中文字 / emoji 都查一本"万国通用字典（UTF-8）"，得到一串电脑能直接算的数字。这一步纯翻译，不做任何合并/拆分判断。

阶段 ④ · BPE 合并（以 " want" 为例）
这一步干啥

对每个 pre-token 的字节序列，按训练时记录好的合并顺序（merges.txt），逐条尝试把相邻字节合并成更大的 token。

以 want 的字节 [32, 119, 97, 110, 116] 为例，演示三步合并：

合并步骤 动作 序列状态
起点5 个独立字节[32, 119, 97, 110, 116]
合并 #142(119, 97) → "wa"[32, "wa", 110, 116]
合并 #291(110, 116) → "nt"[32, "wa", "nt"]
合并 #1503(32, "wa") + (..., "nt") → " want" ✅" want"  → 最终 1 个 token

💡 比喻：就像照菜谱做菜——菜谱第 142 步说"先把 w 和 a 合炒"，第 291 步说"再炒 n 和 t"……你不能跳步、不能改顺序、不在菜谱上的合并永远不做。

⚠️ 关键纠正

BPE 不是"看哪个 token 最长就匹配哪个"。它严格按照训练时记录的合并顺序回放——这点是后面 Part C 要纠正的最大误区。

阶段这一步在做什么本例的具体变化一句话比喻
④ BPE按 merges.txt 顺序合并相邻字节对，输出最终 token5 字节 → 1 个 " want" token照菜谱一步步合炒，不能跳步

把整条流水线想象成一家"token 加工厂"——每个阶段是一个独立的车间，干一件具体的事：

Part C · BPE 深讲：纠正"单步贪心匹配"这个最大误解

关于 BPE 阶段 ④ 到底怎么工作，几乎所有非专业人士都会搞错。这一节用最直白的方式讲清楚。

🔴 最大误区："BPE 就是从左到右找最长能匹配的子串"

这句话听起来很直觉——遇到 "theirs"，先看词表里有没有 "theirs"，没有就找 "their"，再没有就找 "the"……

这不是 BPE。这是另一个完全不同的算法叫"最长匹配分词"（Maximum Match Tokenization）。

如果你带着这个误解去理解 BPE，你看到的代码、读到的论文都会处处对不上。下面分三步讲清楚。

第 1 步 · BPE 有两个完全不同的阶段（很多人搞混的根源）

大多数人把 BPE 当成"一个推理算法"，但其实 BPE 是两个阶段：训练期和推理期。它们做的事完全不一样。

BPE = 训练期 + 推理期（不同的两件事）
🏋️ 训练期（离线，做一次）

规模：万亿 token；耗时：数天/周

输入

海量训练文本

做什么

从字节级开始，反复执行：

  • 统计所有相邻字节对的频次
  • 把出现频次最高的对合并成新 token
  • 记录这次合并到 merges.txt
  • 重复，直到达到目标词表大小

输出（最关键！）

一份带顺序的合并清单：

# merges.txt
#142: 119 97   → "wa"
#291: 110 116  → "nt"
#1503: 32 "wa" → " wa"
...
⚡ 推理期（在线，每次都跑）

规模：一段话；耗时：毫秒

输入

用户的一段话

做什么（核心！）

先走阶段 ①②③，然后按 merges.txt 顺序：

  • 读 merges 第 1 行，扫一遍序列：有 → 全部替换；没有 → 跳过
  • 读 merges 第 2 行，再扫一遍……
  • 一直遍历到 merges.txt 末尾

⚠️ 每条 merge 只查一次！不是循环往复直到收敛

伪代码

tokens = bytes(text)
for (a, b) in merges:
    tokens = replace_all(tokens, (a,b), ab)
# → 最终 tokens 即输出
# → 去查 vocab 拿 ID
🔑 关键洞察

merges 的顺序就是优先级——先训练出来的合并规则，推理时优先使用。这就是为什么 BPE 不是"贪心最长匹配"，而是"按训练顺序回放"。

第 2 步 · 用反例证明"BPE ≠ 贪心最长匹配"

假设训练后的 merges.txt 前几行长这样：

merge #1 :  (t, h)     → th
merge #2 :  (th, e)    → the
merge #3 :  (e, r)     → er
merge #4 :  (ther, s)  → theirs   ← 注意这一条！

现在推理时输入 "theirs"。如果是贪心最长匹配——它会检查"词表里有 theirs 吗？有！直接返回 1 个 token"。

但 BPE 不是这么工作的，它老实按 merges.txt 顺序回放：

步当前序列正在检查的规则是否触发序列变化
初始[t, h, e, i, r, s]——纯字节
1[t, h, e, i, r, s]#1 (t,h)→th✅ 命中[th, e, i, r, s]
2[th, e, i, r, s]#2 (th,e)→the✅ 命中[the, i, r, s]
3[the, i, r, s]#3 (e,r)→er❌ 没有相邻的 (e,r) 了不变
4[the, i, r, s]#4 (ther,s)→theirs❌ "ther" 在序列里根本不存在不变
最终输出 4 个 token：[the, i, r, s]。即使词表里有 "theirs"，BPE 也合不出来！
▎为什么 merge #4 (ther+s) 没生效？

因为 merge #4 要求"ther"和"s"是相邻的两个 token。但 #2 触发后，序列已经变成 [the, i, r, s]——"the" 和 "s" 之间隔着 "i" 和 "r"，它们根本不相邻。

而且 BPE 也不会"回退一步"重新尝试。它就是一条直线走到底——按 merges.txt 顺序，每条规则只检查一次当前的序列。

这就是"按顺序回放"的本质：前面的合并决定了后面合并的可能性空间。

第 3 步 · 那"贪心最长匹配"到底有没有？— 有，但在不同地方

这里很容易混淆。让我们彻底分清：

精确结论：当人们说"BPE 是贪心匹配"，他们通常在混淆这两层：
  • BPE 算法本身（教科书定义）：按 merges.txt 顺序回放——不是贪心。
  • tiktoken 等工业实现：用预编译的 trie 树做贪心最长匹配。这是工程优化，在数学上等价于按 merges 顺序回放，但运行更快。
类比：BPE 算法是一份菜谱（步骤固定）；tiktoken 是熟练厨师记住了"最常做的菜直接抄答案"——结果一样，但他没真的按菜谱一步步执行。两者结果等价，但机制不同。
▎对你产品的实际意义
  • token 数可预测：因为是确定性算法，同一段文本在同一个 tokenizer 下结果完全可复现——这是计费透明的基础
  • 专有名词无法"提示性扩词"：你不能在 prompt 里放一段说明就让 BPE 把"FxSkill"合成 1 个 token——必须重训 tokenizer
  • 拼写错误代价高：因为 merge 顺序固定，常见拼写有 VIP token、错拼只能字节兜底——多烧 30-40% 是常态（Part D 例 2）

▎本节核心要点（30 秒速览）
  1. Tokenizer 是 4 阶段流水线：NFC → 正则 → UTF-8 → BPE，各司其职
  2. 阶段 ② 正则是天花板——决定了 BPE 能合并什么、不能合并什么（如"12345"被强制切成 123+45）
  3. 阶段 ④ BPE = 按 merges.txt 顺序回放，不是贪心最长匹配。这是大多数人的最大误解
  4. BPE 训练期产出 vocab.txt + merges.txt；推理期就是按这份"菜谱"回放
  5. tiktoken 等库用贪心最长匹配做工程优化，结果与 BPE 等价但机制不同

③ 为什么这样 — BPE 的设计哲学与第一性原理

直觉：BPE 做了一件聪明的事

▎BPE 的核心洞察

让高频出现的字符串组合自动获得"VIP 身份"（整 token 编码），低频的就保持拆散状态。

结果形成三层结构：
• 高频词（"the"、"ing"、"tion"、常见中文词）→ 整体 1 token，压缩高效
• 中频词（"antidisestablishmentarianism"）→ 拆成若干子词，信息不丢
• 完全未见过的词 → 退化到字节级，永远不会 OOV（Out-of-Vocabulary）崩溃

第一性原理：这是一个信息论最优压缩问题

用数学语言重新表述：

问题形式化：给定一个文本分布 $P(x)$ 和词表大小上限 $|V|_{max}$，找到一个分词方案 $T$，使得期望编码长度最小：

$$ \min_T \mathbb{E}_{x \sim P}\left[ \text{len}(T(x)) \right] \quad \text{s.t.} \quad |V_T| \leq |V|_{max} $$
其中 $T(x)$ 是文本 $x$ 被 tokenizer $T$ 划分后的 token 序列，$\text{len}$ 是序列长度。

BPE 的做法是贪心近似这个最优解：每次选能带来最大压缩收益的那一对合并。虽然不保证全局最优，但在实践中效果极好——因为自然语言的统计特性给了它一个"友好的"数据分布。

Zipf 定律：自然语言的幂律分布

▎Zipf 定律：BPE 为什么能工作得这么好的底层原因
George Zipf 1949 年观察到：自然语言中词频严格服从幂律分布。
  • 排名第 1 的词（"the"）频次 ≈ 排名第 N 的词的 N 倍
  • 极少数词极高频（"the"、"of"、"and" 占英语文本 ~15%）
  • 大量词极低频（医学、法律、跨境支付术语）
  • 固定词表无论怎么选都会浪费：选高频词漏低频词，选全部词则词表爆炸
BPE 用子词策略巧妙解决：高频词整体收录（~1000-5000 个就覆盖大部分文本），低频词由子词组合表达。这正是幂律分布下的近最优压缩。

不同 tokenizer 对数字的切分方式，直接决定 LLM 的算术与符号推理能力上限。
行业行动时间线：
  1. GPT-2（2019）：允许任意长度数字合并 → "12345" 可能是 1 个 token → 数字内部结构丢失 → 算术表现差
  2. GPT-4 cl100k_base（2023）：引入 \p{N}{1,3} → 强制 3 位切分
  3. LLaMA 3（2024-04）：跟随 GPT-4 采用 3 位规则
  4. DeepSeek-V3（2024-12）：同样 3 位切分
  5. Qwen3 / Mistral / Claude：全部采用类似的数字规则化切分

结果：现代模型在简单算术上的准确率从 GPT-2 的 <30% 跃升到 GPT-4o 的 >95%。
注：2024-2025 年有多篇学术论文（Singh & Strouse 2024、"Token Awareness"框架等）系统解释了这个现象的因果机制。但关键是：4+ 家头部公司在论文大规模引用之前就已经一致采用了这个规则。这是典型的"工程先行，学术后释"。

词表大小本身就是 Scaling Law 的关键维度

长期以来，人们关注 scaling law 时只看"参数量 × 数据量 × 算力"。但 2025 年 ByteDance ICML 论文《Over-Tokenized Transformer》给出了一个反直觉的发现：

▎词表扩大 2 倍 ≈ 参数翻倍的效果（几乎零额外推理成本）

核心发现：在相同计算预算下，把词表从 V 扩大到 2V，效果接近把模型参数从 P 扩到 2P。


为什么？直觉上：

  • 更大词表 → 更多"整词 token" → 同样的意思用更少的 token 表达 → 有效上下文更长
  • 更多 token → embedding 层参数增加（V × d_model）→ 表达能力提升
  • 但推理时的 自注意力计算量取决于序列长度 L，不是词表大小 V → 大词表不增加推理延迟

行业验证：Qwen3.5 把词表从 Qwen3 的 151,669 扩到 250,000，官方报告编码效率提升 10–60%（不同语言差异）。这直接验证了上述理论。

第一性原理总结：Tokenizer 的本质是在做有损压缩，BPE 通过统计驱动的子词策略实现了对幂律分布语言的高效近似；而词表大小 V 本身是一个独立的 scaling 维度——扩大 V 的性价比远超同等规模的参数扩大，因为前者只增加 embedding 层参数（一次性查表），后者增加每层计算（每次推理都要执行）。

BPE vs One-Hot：为什么不直接用朴素方案

方案词表 V=100K 时致命缺陷
One-Hot每 token 一个 100K 维超稀疏向量，99.999% 为 0所有 token 互相正交（距离相等），无法表达"美元"比"番茄"更接近"日元"
BPE + Embedding每 token 映射为一个 4096/7168 维稠密向量语义相近的 token 在向量空间中自然聚集 — 这是 Embedding 章节（1.2）的内容

LLaMA 架构切换的意义：这相当于一家公司把自己的基础设施从 iOS 换到了 Android——成本巨大，除非新方案有明显优势。Meta 这一切换证明了 BBPE+tiktoken 方案的成熟度。

词表增长时间线：3 年 8 倍

这是 2023-2026 tokenizer 领域最显著的趋势：

前沿探索：BLT（Byte Latent Transformer）— 研究前沿 ≠ 行业共识

▎BLT：彻底抛弃 tokenizer 的激进想法

Meta + Stanford 提出的 Byte Latent Transformer (ACL 2025) 走得更远：不做任何 tokenization，直接把原始字节序列喂给模型。


发展脉络：

  • 2024：原始 BLT 论文发布
  • 2025-05：Meta 开源 BLT 权重到 HuggingFace
  • 2025-09：HuggingFace transformers 正式集成
  • 2026-05：Fast BLT（BLT Diffusion） 解决逐字节生成瓶颈 (arxiv 2605.08044)

但是：截至 2026-05，没有任何生产级模型采用 BLT 作为主 tokenizer。OpenAI / Meta / Google / DeepSeek / Qwen 全部仍在用 BPE。BLT 是重要的研究方向，但属于"研究前沿"而非"行业共识"。

新维度：特殊 Token 的爆发式增长

一个容易被忽视的变化：LLaMA 4 的特殊 token 从 256 个暴增到 2,048 个（8 倍），其中新增了 thinking_start / thinking_end 等 reasoning token。这意味着 tokenizer 不再只是"分词工具"，还开始承载模型的推理控制信号功能——这是 §④ 演进节的最新维度。

⑤ 产品决策 — Tokenizer 如何影响你的 Agent 设计

▎与你工作的直接连接
  1. 成本估算：DDAgent 提示词如果有大量中文专有名词，token 消耗显著高于英文场景——给老板汇报 API 成本时这是关键变量
  2. 上下文窗口规划：KBA 知识库如果以中文为主，128K 上下文实际只能装约 40K 中文字符——影响检索粒度和 RAG 分块策略
  3. 模型选型：优先选择大词表模型（200K+）。2025年后头部模型中文效率差距在缩小，o200k_base / Qwen3.5 / Gemini 3 对中文的支持已大幅改善
  4. 幻觉根因分析：当 Agent 对专有名词（"FxSkill"、"TenPay Global"）反复出错，可能是 tokenizer 将其切碎导致模型学不到稳定表征。选大词表模型本身就是一种解法
  5. 词表与推理成本的关系：扩大词表不显著增加推理延迟（注意力计算量取决于序列长度 L，非词表 V），但能显著降低 token 消耗——这是 ByteDance ICML 2025 + Qwen3.5 双重验证的结论

今日核心要点（30 秒速览）

  • 模型不直接处理文本，Tokenizer 先将其转为 token ID 序列
  • Token 不等于字也不等于词——它是 BPE 统计学习得到的高频字节组合
  • 工业 BPE = 4 阶段确定性流水线（归一化 → 正则预分词 → 字节化 → BPE 合并），其中预分词规则是天花板
  • BPE 本质是对幂律分布语言的有损压缩最优近似；词表大小 V 是独立的 scaling 维度（扩大 V 性价比超过扩大参数）
  • Byte-level BPE 是行业绝对主流（5/7 家头部公司），LLaMA 从 SentencePiece 切换到 tiktoken 是标志性事件
  • 词表 3 年 8 倍增长（32K → 262K），驱动力：多语言 + 效率 + scaling law
  • 选模型时优先大词表（200K+）：不增延迟，降 token 消耗，改善专有名词处理
