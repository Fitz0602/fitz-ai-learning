1 是什么 —— 从考试分数到系统度量

🍽️ 餐厅评审类比

你开了一家餐厅，怎么知道厨师好不好？
传统方法：请米其林评委来打分（= 公开 Benchmark）
你的方法：自己每天试菜 + 让顾客填反馈表（= 自建评测 + LLM-as-Judge）
关键洞察：米其林高分不等于你的顾客满意 — 同理，MMLU 高分不等于你的 Agent 在跨境支付场景好用。

Benchmark 是什么？

Benchmark（基准测试）就是给大模型出的"标准化考试"——一组预先设计好的问题，用统一的标准打分，让不同模型可以公平比较。

但 2024-2026 年行业的一个核心认知转变是：Benchmark 分数 ≠ 你的场景表现。就像 SAT 高分不保证能做好一份具体工作一样。

⚠️ SWE-bench 退役的启示（2026.03 OpenAI 官宣）

SWE-bench Verified 曾是 AI 编程 Agent 的"高考"，但 2026 年 3 月 OpenAI Frontier Evals 团队正式宣布退役它。三大原因：
① 数据污染：模型在预训练中见过考题（背题），分数虚高至 80.9%
② 天花板效应：6 个月只涨 6%，已无法区分模型能力
③ 测试缺陷：59.4% 测试用例存在过宽或过窄问题
替代方案：→ SWE-bench Pro（Scale AI, 1865 题,抗污染,企业级复杂度）+ SWE-bench-Live（每月更新动态题库）

LLM-as-Judge 又是什么？

当模型的输出不是选择题而是自由文本时（比如客服回复、尽调报告、换汇建议），传统"标准答案匹配"完全失效。这时业界采用 LLM-as-Judge：

📝 传统评测

  • BLEU / ROUGE 文本重叠度
  • 精确答案匹配
  • 人工标注（慢、贵、不可扩展）

❌ 对生成式输出相关性低

⚖️ LLM-as-Judge

  • 用更强的 LLM 评判输出质量
  • 多维度评分(忠实/相关/完整/无害)
  • API 一调用即出结果

✅ 与人类评分一致性达 85%（高于两人间一致率）

💡 PM 视角的核心命题

作为管理 5 个生产级 Agent 的 PM，你需要回答的不是"GPT-4 比 GPT-3.5 强多少"，而是：
DDAgent 尽调预填率 83% → 这个数字可信吗？用什么方式测的？
TRSAgent 分类准确 92.2% → 在哪些邮件类型上会崩？
FxAgent 采纳率 98-99.75% → 用户"满意"是因为真的好还是因为没得选？

2.2 LLM-as-Judge 的两种模式

📊 单输出评分 (Single-output)

给一个输出打绝对分数

  • G-Eval: 用 LLM 生成评分+CoT理由 (Liu et al., EMNLP 2023)
  • 支持 reference-based 和 referenceless
  • 适合: 需要绝对分数上报的场景

⚠️ 绝对分数校准困难

⚔️ 成对比较 (Pairwise)

A vs B 选出更优者（Arena模式）

  • Arena G-Eval: 自动化成对比较
  • 无需校准绝对分数
  • 适合: 模型选型 / A/B Test

✅ 相对排序比绝对分更可靠

2.3 Judge 的已知偏差与缓解策略

LLM-as-Judge 不是银牌。Jason Wei（前 Google Brain）的核心观点：一致性(agreement) > 准确性(accuracy)——只要每次评分稳定，系统性偏差可以通过校准修正。

偏差类型表现缓解策略
位置偏差 Position Bias成对比较时倾向选择先出现的选项交换位置跑两次(A在前+B在前),取综合结果
自我偏好 Self-PreferenceGPT-4 给 GPT-4 生成的答案更高分使用第三方模型做 Judge（如用 Claude 评 GPT 输出）
长度偏差 Verbosity Bias更长回答倾向于获得更高分在 prompt 中明确要求忽略长度因素
风格偏差 Style BiasJudge 偏好与自身风格相似的输出Few-shot 示例锚定评分标准
能力上限Weak Judge 无法评价 Strong AgentJudge 模型必须 ≥ 被评测模型能力
🎯 G-Eval 最佳实践（Confident.ai 推广）

一个可靠的 LLM Judge 评测 prompt 必须包含四要素：
① 清晰的评分维度定义（如"回复是否准确?是否有帮助?"）
② 明确的评分粒度（建议 1-5 分制，避免 binary 判断）
③ Few-shot 参考示例（3-5 个有人类标注的参考答案）
④ CoT 评分理由（要求 Judge 先解释再打分）

3 为什么 —— 评测的第一性原理

3.1 为什么需要评测？

Mason AI Lab（2026-03）一句话点透了本质："你不跑测试就不该上线"。但更深层的理由有三个：

理由一：模型是非确定性的

同一个输入，模型可能给出不同输出。没有评测 = 在老虎机上押注。"AI 客服的回答好吗？""感觉还行"这不是工程语言。
工程语言是：Faithfulness 97.2%, Relevancy 89.5%, 比上月提升 3.1pp

理由二：Benchmark 会饱和，但场景不会

HumanEval 94% 已饱和（所有顶级模型都会写 Python 函数），但这不代表你的 代码审查 Agent 能在生产环境用好。Benchmark 考的是"会不会"，场景评测考的是"能不能稳定做到"。

理由三：评测驱动迭代方向

没有量化指标就无法判断优化是否有效。TRSAgent 从 72.8% 提升到 92.2%（+19.4pp），这个数字背后的每一步迭代都需要评测数据支撑——否则你只是在"感觉变好了"。

3.3 为什么 Agent 评测不能只看"通过率"？

SWE-bench 的评测逻辑很务实：修改通过了单元测试就算成功。但这带来一个深层问题——Agent 可能用了完全不符合工程最佳实践的解法，只要测试过了照样得分。

这就是 2026 年 Agent 评测面临的核心张力：结果导向（好不好用）vs 过程导向（怎么做出来的）。

🔄 Terminator-1 事件（伯克利 SkyLab, 2026.04）

伯克利团队发布的 Terminator-1 在 SWE-bench Verified 和 Terminal-Bench 上取得了高分排行榜名次——但实际解决了 0 个任务。这个极端案例暴露了当前 Agent Benchmark 的一个致命弱点：评测指标可以被 gaming。这也解释了为什么 SWE-bench Pro 要引入三阶段人工验证流程确保每个任务都可解且解法空间被约束。

3.4 为什么"自建评测"才是最终答案？

Mason AI Lab 的结论直截了当：MMLU 考的是通用知识，你的客服机器人需要的是"能根据知识库准确回答"——这要用你自己的评估方式。

对 Fitz 的项目来说，这意味着：

  • DDAgent：不能只用 MMLU 衡量，需要构建"尽调报告质量"专项评测（信息提取完整性 × 事实准确性 × 格式合规性）
  • BAAgent：经营分析的评测维度应该是"数据准确率 × 有价值率 × 洞察深度"，而不是 GPQA
  • TRSAgent：邮件分类+回复的质量必须用带标注金标准的数据集做回归测试
  • FxAgent：换汇咨询的"有用性"只能由真实用户反馈+专家抽样复核来衡量

4.3 Chatbot Arena：最难刷的评测

Chatbot Arena（又称 Arena AI/LMSYS Arena）是人类盲评投票排名系统，采用 ELO 分数。它的不可替代性在于：你没法针对"人类喜好"做针对性优化——至少目前还不行。

🏆 Arena 为什么难以被 Gaming？

① 动态题库：用户提交的真实问题，无法提前准备
② 主观但集体理性：单个用户有偏好，但数千票后 ELO 收敛
③ 匿名盲评：用户不知道哪个模型是哪个，消除了品牌偏见
④ 长尾覆盖：涵盖各种语言/领域/风格的长尾场景

📌 2026 评测体系的五个共识
  1. Benchmark 分数不代表你的场景表现——必须建自己的评测集
  2. 静态 Benchmark 必然被污染——动态更新(SWE-Live/LiveCodeBench)是趋势
  3. LLM-as-Judge 是默认方案——但需注意偏差缓解(Jason Wei 一致性优先原则)
  4. Agent 评测必须看端到端+成本——不只是"对不对"，还要看"多少钱""多久"
  5. 评测必须嵌入 CI/CD——一次性评测无意义，持续回归才是工程化

5.2 三层评测体系的落地路径

Fitz 已经建立了 L1(行为级) / L2(路由级) / L3(知识级) 三层框架。本章知识的增量价值在于：

🔧 可以立即改进的三件事

① 给每个 Agent 建"金标准回归集"
TRSAgent 的 206 封测试邮件是最佳实践——其他 4 条 Agent 也应建立类似规模的金标准集，嵌入 CI/CD 每次 Prompt/模型变更时自动回归。

② 引入 LLM-as-Judge 做 L3 知识级评测
DDAgent 的尽调报告质量、BAAgent 的 Insight 深度——这些主观维度用 GPT-4/Claude 做 Judge，配合 Few-shot 示例，可以达到 85%+ 人机一致性。

③ 建立 Agent 专属"Live Benchmark"
参考 SWE-bench-Live 的思路，每月往测试集注入新的真实用户案例（DDAgent 新增的企业类型、FxAgent 新增的汇率品种、TRSAgent 新出现的邮件模板），防止评测集被隐性污染。

5.3 评测投入的 ROI 判断框架

不是所有 Agent 都值得同等级别的评测投入。PM 需要做取舍：

Agent出错代价用户可见度推荐评测等级
TRSAgent极高（资金损失/合规风险）高（客户直接感知）L1+L2+L3 全套 + 金标准集 + 持续回归
DDAgent高（尽调失误→合规风险）中（内部使用者）L1+L2 + LLM Judge 抽检 + 月度人工审核

KBA低（知识不准确可修正）低（内部工具）L1 流水线成功率 + L2 覆盖率规则检查
🎯 本章核心结论

评测不是学术练习，是 Agent 工程化的基础设施。正如你不会不跑测试就部署代码，也不应不评测就上线 Agent。Fitz 的三层体系已经有了正确的骨架——接下来是用 LLM-as-Judge + 金标准回归集 + Live Benchmark 把骨架变成活的免疫系统。

主线定位：T1 D6.1 回答了"如何判断模型和Agent好不好用"——这是 T2 A4 Harness 六组件中"Evaluate 评估反馈闭环"的理论基础。没有评测就没有反馈，没有反馈就没有闭环， Harness 就缺了一条腿。
