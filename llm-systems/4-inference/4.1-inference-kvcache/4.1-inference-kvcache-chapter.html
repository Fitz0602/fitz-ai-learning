1 是什么：LLM 推理的两阶段本质

LLM 推理就像厨师做一道菜：先一次性读完整个菜谱（Prefill），然后一步一步按菜谱操作出菜（Decode）。菜谱越长，读的时间越长；但每出一道菜，你不需要重新读菜谱——你记住了之前读的内容，这就是 KV Cache。

自回归解码：一次一个 Token

LLM 生成文本的本质是自回归（autoregressive）：每一步基于前面所有 token 的上下文，预测下一个 token。假设输入 prompt 有 $n$ 个 token，输出 $m$ 个 token，模型总共需要做 $n + m$ 次前向传播中的注意力计算。

关键洞察：第 $t$ 步的注意力计算需要所有 $1 \sim t$ 个 token 的 Key 和 Value 向量。如果每步都从头算，计算量是 $O(t^2)$，随序列长度二次增长——这不可接受。

Prefill 与 Decode：两种完全不同的计算模式

LLM 推理自然分为两个阶段：

在 H100 GPU 上，处理 10,000 个 token 的 prompt 只需 200-400ms（Prefill），但 Decode 阶段每个 token 需要 25-40ms。这就是为什么输出 token 的成本通常是输入 token 的 3-10 倍（Morph 2026 数据）。

LLM 推理 = Prefill（算力瓶颈）+ Decode（内存瓶颈）。两个阶段的瓶颈完全不同，这决定了后续所有优化策略的方向：Prefill 优化计算效率，Decode 优化内存效率。

2 怎么实现：KV Cache 的机制与数学

KV Cache 就像你在考试时做的"笔记"：你已经算出的中间结果（Key/Value 向量），不需要每道题都重新算一遍，直接查笔记就行。笔记的代价是占桌面（显存），但省下的时间（避免重复计算）远超占桌的成本。

没有 KV Cache 的世界

假设一个 LLM 有 $L$ 层、$H$ 个注意力头、每个头的维度 $d_k$。生成第 $t$ 个输出 token 时，如果不缓存，注意力需要重新计算所有 $t$ 个 token 的 Key 和 Value：

$$\text{计算量（无缓存）} = O(t^2 \cdot L \cdot H \cdot d_k)$$

对于 $t = 10000$ 个 token，这意味着 1 亿次乘法——只是为了生成第 10001 个 token。

有 KV Cache 的世界

KV Cache 的核心思想：第 $t$ 步只需要计算新 token 的 $K_t, V_t$，历史 token 的 $K_{1:t-1}, V_{1:t-1}$ 直接从缓存读取。

$$\text{Attention}(Q_t, K_{1:t}, V_{1:t}) = \text{softmax}\left(\frac{Q_t K_{1:t}^T}{\sqrt{d_k}}\right) V_{1:t}$$

每步的计算量从 $O(t^2)$ 降为 $O(t)$——线性而非二次。

KV Cache 的显存占用计算

对于一个模型的 KV Cache，显存占用公式：

$$\text{KV Cache Size} = 2 \times L \times S \times H_{kv} \times d_k \times \text{dtype\_size}$$

其中 $L$ = 层数，$S$ = 序列长度，$H_{kv}$ = KV 头数（GQA 下小于 $H$），$d_k$ = 每个头的维度。

模型LH_kvd_k128K上下文 KV Cache

常见误区：以为 KV Cache 只占"一小块"显存。实际上，在 70B 模型 + 128K 上下文的场景下，KV Cache 可以吃掉 40-80GB 显存——比模型权重本身还多！这就是"Memory Wall"：推理的瓶颈不在计算，而在存储。
KV Cache 将每步注意力计算从 $O(t^2)$ 降为 $O(t)$，代价是显存随序列长度线性增长。GQA/MQA 减少缓存体积（$H_{kv} \ll H$），MLA 进一步通过低秩压缩将缓存压缩到极致。

3 为什么：Memory Wall 与碎片化的第一性原理

传统 KV Cache 管理就像在停车场的每个车位上放一个"已预订"标志——即使车还没来，车位也不能给别人用。PagedAttention 则像停车场真正按需分配：车来了才占位，走了就释放，不同车位不需要连续。

第一性原理：为什么推理慢？

推理延迟的根本原因不是"算力不够"，而是内存带宽不够。Decode 阶段每个 token 的前向传播：

$$\text{Decode 延迟} \approx \frac{\text{模型权重大小} + \text{KV Cache 大小}}{\text{GPU 内存带宽}}$$

在 H100 上（3.35 TB/s 带宽），一个 70B FP8 模型的权重约 70GB，一次 Decode 读取权重就需要约 21ms——与实测 25-40ms 吻合。GPU 的算力单元在等内存总线搬数据，利用率只有 5-10%。

连续内存分配的三大问题

传统推理系统为每个请求预分配最大长度的连续 KV Cache，导致：

问题描述浪费率
内部碎片预分配最大长度，实际输出往往短很多20-40%
外部碎片不同请求长度不同，释放后产生无法复用的小块15-30%
预留浪费为未来 token 预留的空间，在生成前无法供其他请求使用10-25%

根据 vLLM 论文（SOSP 2023）的实测，传统系统的 KV Cache 有效利用率仅 20.4%-38.2%——超过 60% 的显存被浪费了。

内存共享机会的错失

在 Agent 场景中，多个请求共享相同的系统提示词（System Prompt）。传统连续内存方案下，每个请求独立存储 System Prompt 的 KV Cache，无法跨请求复用。

推理慢的根因是 Memory Wall：Decode 阶段 GPU 95% 的时间在等内存搬运。传统连续内存分配导致 60%+ 的显存浪费，严重限制了批处理大小和吞吐量。优化方向不是"更快地算"，而是"更省地存"。

4 演进格局：从 PagedAttention 到分布式推理（2023-2026）

Era 2 深入：PagedAttention（2023，vLLM，SOSP 2023）

PagedAttention 借鉴操作系统虚拟内存的分页思想，将 KV Cache 划分为固定大小的块（Block），每个块存储固定数量（默认 16）的 token 的 KV 向量。每个请求维护一个块表（Block Table），记录逻辑块到物理块的映射。

特性传统连续分配PagedAttention
内存碎片内部 + 外部，60%+ 浪费仅最后一个块未满，浪费 <4%
分配策略预分配最大长度按需动态分配
跨请求共享不支持Copy-on-Write 共享
显存利用率20-38%95%+

Era 3 深入：前缀缓存与异构 KV

RadixAttention（SGLang）用基数树（Radix Tree）维护 KV Block 的 LRU 缓存，支持跨多次生成的自动复用。在 Agent、思维树等复杂场景中缓存命中率远高于 vLLM 的块级哈希匹配。

FlashInfer（MLSys 2025 最佳论文）统一了 Page/Radix/Tree 等异构 KV Cache 布局为块稀疏行（BSR）矩阵，通过 JIT 编译生成定制注意力内核。集成到 vLLM/SGLang 后，inter-token 延迟降低 29-69%。

异构 KV Cache（2024）处理混合架构：MoE 的稀疏激活、VLM 的视觉编码器、SWA 的滑动窗口——Llama 3.2 11B Vision 如果统一管理，内存浪费达 79.6%（Jenga 论文数据）。

Era 4 深入：PD 分离架构（2025-2026）

核心洞察：Prefill 受算力约束，Decode 受内存带宽约束——两者适合不同硬件配置和并行策略。

$$\text{PD 分离加速} \approx \frac{\text{Prefill 专用 GPU} + \text{Decode 专用 GPU}}{\text{混合 GPU 的互相干扰}} \approx 1.5\text{x-}4.5\text{x}$$

投机解码：绕过 Memory Wall 的另一种思路

投机解码用一个小型草稿模型一次预测 K 个候选 token，目标模型一次前向传播验证全部——利用了 Transformer 天然产生每个位置概率分布的特性。EAGLE-3 / Medusa 可实现 2-3x 加速，Apple 的 Mirror-SD 更达 5.8x。关键保障：输出分布与原始模型 bit-exact 相同，不是近似。

KV Cache 优化四代演进：① 连续分配 → ② PagedAttention（消除碎片） → ③ 前缀缓存 + 异构 KV（复用+混合架构） → ④ PD 分离 + 投机解码（架构级优化）。2026 年行业共识：vLLM/SGLang/TensorRT-LLM 全部基于 PagedAttention，PD 分离从实验走向标配。

5 与产品连接：Agent 成本 = KV Cache 成本

DDAgent 处理一笔跨境汇款投诉时，System Prompt 约 2000 token，多轮对话累积到 10000+ token。每轮对话都要把整个历史"喂"给模型——这不是"读一遍"，而是把历史 KV Cache 搬进 GPU 内存。10000 token 的 KV Cache 在 70B 模型上约 3GB。5 个并发 Agent = 15GB，光 KV Cache 就吃掉一张 A100 40GB 的 37%。

Agent 场景的 KV Cache 特征

Agent 与普通 Chat 的本质区别：上下文持续累积，多轮互动，大量共享前缀。DeepSeek + 清华的 DualPath 论文指出，Agent 场景 KV Cache 命中率通常 >95%。

从 KV Cache 理解 Context 工程的物理约束

3.2 章学了 RLHF/DPO 塑造模型行为，但 Agent 的 Context 管理还受物理约束：KV Cache 的大小决定了你能塞多少上下文，PD 分离的延迟决定了 Agent 能多快响应。这就是主线连接句说的"KV Cache 是 Context 工程的物理约束"——A3.1（Context Engineering）章节将深入这个约束。

Agent 成本 = KV Cache 成本。Agent 场景的特征是"长上下文 + 短追加 + 高前缀复用"，对应的优化策略是前缀缓存 + PD 分离。推理引擎选型取决于场景：共享前缀多选 SGLang，通用场景选 vLLM，极致吞吐选 TensorRT-LLM。下一章（4.2 量化+Serving）将从另一个角度降成本。
