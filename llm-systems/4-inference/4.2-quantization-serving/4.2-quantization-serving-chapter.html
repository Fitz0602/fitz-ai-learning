1 是什么：量化是有损压缩，蒸馏是知识迁移

把一个 70B 参数的大模型想象成一部 4K 高清电影。量化就是把电影从 4K 压缩到 1080p 甚至 720p——文件变小了，大部分时候你看不出区别，但极端场景下细节会丢失。蒸馏则是请导演写一份精简版剧本给新人演员照着演——新人没看过原片，但学会了导演的核心表达手法。

量化的核心直觉

神经网络中的每个参数（权重）在训练时用 FP32（32 位浮点数，约 $4.29 \times 10^9$ 个可能值）或 BF16（16 位）存储。量化（Quantization）的目标是用更少的比特表示这些权重：

  • INT8: 256 个可能值 → 模型体积缩小 ~50%
  • INT4 / 4-bit: 16 个可能值 → 模型体积缩小 ~75%
  • FP8: 用 8 位浮点保留动态范围 → 缩小 ~50%，质量损失极小

关键洞察：不是所有参数都同等重要。LLM 的权重分布高度不均匀——大部分权重集中在接近 0 的区域（贡献小），少数"异常值"（outlier）承载了模型的关键能力。量化本质上是在"哪些精度可以牺牲"和"哪些必须保真"之间做权衡。

蒸馏的核心直觉

知识蒸馏（Knowledge Distillation）是另一条路：不压缩同一个模型，而是训练一个更小的"学生模型"来模仿更大的"教师模型"。教师模型的输出（概率分布、中间层特征、推理链路）成为学生模型的学习信号。

2 怎么实现：四大量化方法 + 三大 Serving 引擎

2.1 量化四巨头：GGUF / GPTQ / AWQ / FP8

2026 年的量化生态已经收敛到四个主流格式，各自占据明确的生态位：

格式定位精度硬件代表工具
GGUFCPU / 端侧 / Apple Silicon 通用格式Q2_K ~ Q8_0CPU + GPUllama.cpp, Ollama
GPTQNVIDIA GPU 服务端推理先驱INT4/INT8NVIDIA onlyvLLM, TGI
AWQ当前 GPU 生产部署最佳实践INT4NVIDIA (Marlin kernel)vLLM, AutoGPTQ
FP8Hopper/Blackwell "准无损"标准E4M3/E5M2NVIDIA Ada+vLLM native, TensorRT-LLM

GPTQ：GPU 量化的开拓者

GPTQ（Frantar et al., 2023）的核心思路：利用 Hessian 信息找到"可以安全降低精度"的权重。算法对权重矩阵按列逐个处理，每次量化一列后更新剩余列的误差——这是一个类似回溯的迭代过程。

$$W_{quant} = \text{round}\left(\frac{w}{s}\right) \cdot s, \quad s = \frac{\max(|w|)}{2^{b-1}-1}$$

其中 $s$ 是每组的缩放因子（scale），$b$ 是目标位数。GPTQ 的关键创新在于误差反馈：量化第 $i$ 列产生的残差会传播到后续未量化的列上。

优点：理论严谨，INT4 质量稳定。缺点：量化速度慢（70B 模型需 15-30 分钟），需要校准数据集敏感，仅支持 NVIDIA GPU。

AWQ：激活感知的实用主义

AWQ（Lin et al., 2023）换了一个角度：权重的 importance 不是由权重本身决定的，而是由它所连接的激活值（activation）幅度决定的。如果某通道的激活值总是很大，说明这个通道的权重对输出影响更大——这些权重应该被保护起来。

AWQ 的直觉：想象你在整理书架。GPTQ 的方式是根据书的厚度决定是否压扁；AWQ 的方式是根据这本书被翻阅的频率决定是否压扁。常被翻阅的书（高激活通道的权重）即使薄也要好好保存。

AWQ 的做法很简单：识别 top 1% 的"显著权重"（salient weights）保持高精度，其余激进量化到 INT4。实际效果：

  • 量化速度比 GPTQ 快 3-5×（无需反向传播）
  • 相同 bit-width 下质量通常优于 GPTQ 1-3%
  • 配合 Marlin 推理内核可达 ~741 tok/s（H200 benchmark）

截至 2026 年中，AWQ 已成为 vLLM 生产部署的首选 INT4 格式。HuggingFace 上 AWQ 格式下载量超过 1900 万次。

GGUF：端侧通吃的瑞士军刀

GGUF 是 llama.cpp 项目定义的文件格式——一个文件包含量化权重、tokenizer、元数据全部内容。下载一个 GGUF 文件就能在任何设备上运行。

GGUF 的命名规则直接告诉你精度级别：

级别平均 bit/weight7B 模型大小适用场景
Q2_K~2.5~2.3 GB极限压缩，质量损失明显
Q4_K_M~4.5~4.5 GB推荐默认选项
Q5_K_M~5.5~5.5 GB质量优先
Q8_08~7 GB近无损

K-quant 方法是 GGUF 的杀手锏：对不同层的权重使用不同精度（attention 层高精度、FFN 低精度），在总 bit 预算内最大化保留信息。Q4_K_M 在大多数任务上能保留原模型 95%+ 的质量。

GGUF 的生态统治力：Ollama、LM Studio、GPT4All 全部原生支持。但它的弱点也明确——GPU 推理性能不如 GPTQ/AWQ（因为设计初衷是 CPU-first）。

FP8：Hopper 时代的"准无损"新基准

FP8 是 2024-2026 年最大的范式转变之一。NVIDIA Hopper（H100/H200）和 Blackwell 架构原生支持 FP8 Transformer Engine，使得：

  • 相比 BF16：内存减半，速度提升 ~33%
  • 质量损失：0.1-0.3% PPL 增加（几乎所有任务上近乎无损）
  • 两种子格式：E4M3（精度优先，用于权重）和 E5M2（动态范围优先，用于梯度）
2026 选型速查：RTX 5090/4090 + Hopper 卡 → FP8 是"免费午餐"；RTX 3000 系列 → 无硬件加速，用 AWQ/GPTQ INT4；Apple Silicon / CPU → GGUF Q4_K_M。

2.2 KV Cache 量化：被忽视的显存黑洞

大多数人只关注权重量化，但KV Cache 才是长上下文场景的真正显存瓶颈。一个 Q4_K_M 量化的 7B 模型权重只占 ~4GB，但 32K context 的 KV Cache 可以轻松吃掉额外的 4-8GB——而且随着对话轮次增长持续膨胀。

vLLM 和 llama.cpp 都支持独立的 KV Cache 量化：

  • QServe (MIT HAN Lab): W4A8KV4 方案——4-bit 权重 + 8-bit 激活 + 4-bit KV Cache，端到端协同设计
  • SpinQuant (Meta): 学习正交旋转矩阵重塑激活分布，使 W+A+KV 统一到 4-bit 时损失 <3%（此前同类方法降级 25%+）
  • SmoothQuant: 将激活值的 outlier 迁移到权重上，数学等价变换使双方都更容易量化

2.3 Serving 引擎三强：vLLM / SGLang / TensorRT-LLM

光有量化还不够——你需要一个引擎把这些优化后的模型高效地服务出去。2026 年的生产级 LLM Serving 被三个引擎瓜分：

vLLM：为什么它是默认选择？

vLLM 的核心竞争力来自两个基石创新——它们直接回答了"为什么传统 serving 浪费了这么多 GPU 资源"：

PagedAttention：像操作系统管理内存一样管理 KV Cache

传统引擎为每个请求预分配最大可能的连续 KV Cache 内存块。如果 max context = 128K tokens 但平均只用 2K，98% 的内存闲置浪费——内部碎片高达 60-80%。

PagedAttention 从操作系统的虚拟内存借鉴思路：将 KV Cache 切成固定大小的 page（通常 16 tokens/page），通过 block table 映射逻辑位置到物理内存，按需分配。结果：内存碎片降到 <4%，同样 GPU 能塞下更多并发请求。

Continuous Batching：token 级调度消除空闲等待

传统 Static Batching 把 N 个请求凑一批，全部跑完才接下一批。如果某个请求生成 1000 token 其余只生成 10 个，GPU 就傻等着慢请求结束。Continuous Batching 在每个 token 步骤后重新组织 batch——完成的请求踢走，排队的新请求插入。GPU 利用率从 ~30% 飙升到 >90%。

常见误区："vLLM 比 Ollama 快所以应该用 vLLM。" —— 不对。vLLM 设计目标是高并发服务端（几十上百用户同时请求）。单用户交互式场景（你一个人跟 AI 聊天），Ollama + GGUF 的首 token 延迟可能更低，因为省去了 batching 开销。匹配引擎到场景才是正解。

SGLang：RadixAttention + 结构化输出的利器

SGLang（LMSYS Org，2024）的差异化来自 RadixAttention——一种基于前缀树（radix tree）的 KV Cache 共享机制。当多个请求共享系统提示、tool schema 或多轮对话历史时，RadixAttention 自动去重共享前缀，缓存命中率 75-95%，在这些场景下吞吐比 vLLM 再高 10-20%。

此外 SGLang 有自己的前端编程语言（SGLang program），支持声明式的结构化输出和复杂多步生成模式，在 Agent Loop 场景中有 2-3× 吞吐优势。xAI 和 DeepSeek 内部重度使用。

TensorRT-LLM：NVIDIA 的终极武器

TensorRT-LLM 通过自定义 CUDA kernel fusion、tensor layout 优化、硬件特定指令调度榨干每一滴 GPU 性能。代价是：

  • 每次更换模型需要 10-30 分钟编译
  • 仅支持 NVIDIA GPU（且模型覆盖有限，需要转换）
  • 工具链深度绑定 NVIDIA 生态，可移植性差

适合的场景：单一模型长期运行、不频繁更换、追求极致吞吐（如大规模在线 API 服务）。Clarifai benchmark：GPT-OSS-120B 在 2×H100 上，TensorRT-LLM 单请求吞吐最高，但 vLLM 在高并发（100 requests）下达到 4741 tok/s 且 TTFT 最快。

3.2 为什么不能无限压？质量悬崖

量化不是免费的——存在明确的质量悬崖（Quality Cliff）。研究（ParetoQ, 2026）揭示了一个反直觉的发现：

ParetoQ 的核心发现（2026）：bit 数和准确率的关系不是平滑曲线。在 3-4 bits 区间，量化行为像"压缩"——去掉冗余信息；但在 ≤2 bits 时，模型学到了根本不同的表征（different representations）。这意味着：固定预算下，用一个更大的模型压到 2-bit，效果反而比用一半参数量的模型压到 4-bit 更好。

3.3 Serving 效率的本质：受限于 memory bandwidth

理解 Serving 性能的关键洞察：LLM 解码阶段是 memory-bound（内存带宽受限）而非 compute-bound。

Decode 阶段每个新生成的 token 只需要做一次矩阵乘法（加载整个权重矩阵 × 一个向量），计算量很小但需要把所有权重从显存读到计算单元。因此：

$$\text{Decode Throughput} \approx \frac{\text{Memory Bandwidth}}{\text{Model Size (bytes)}}$$

这就是为什么：

  • 量化直接提速：模型大小 ↓ 4x → 理论 decode throughput ↑ 4x（实际 2-3x，受 kernel 效率约束）
  • 更好的 GPU 不一定更快 decode：H100 vs A100 的计算峰值差 3×，但内存带宽只差 1.6×——decode 阶段差距没那么大
  • PagedAttention 的价值：更多 batch → 更高的内存带宽利用率 → 更高有效吞吐

4.3 蒸馏的最新进展

知识蒸馏在 2025-2026 年有几个值得注意的动向：

发现 1：强老师未必更好（2026.05 最新论文）

Lu & Liu (arXiv:2605.23857, 2026.05) 的实验挑战了常识：蒸馏预训练不一定需要强 teacher。通过控制模型大小和训练 token 量，他们创建了 strong→weak、same-level、weak→strong 三种 teacher-student 关系，发现：

  • 即使小而欠训练的 teacher 也能改善更大的 student
  • 更强的 teacher 并不总是更好——push 太多可能饱和甚至反转收益
  • 蒸馏对泛化能力（OOD / downstream）的提升大于 in-domain 拟合

发现 2：难度感知蒸馏（D2A2, Expert Systems 2026.05）

D2A2 框架将"问题的内在难度"（通过 LLM 决策不确定性度量）融入蒸馏过程：过滤阶段优先保留困难样本，训练阶段动态调整对困难样本的关注权重。用更少的数据超越了现有方法。

发现 3：Concrete Score Matching (CSD, arXiv:2509.25837)

提出离散分数匹配目标，克服 softmax 平滑和 logit shift 不变性两个限制，在 GPT-2/OpenLLaMA/Gemma 上一致超越近期 KD 目标。

5.1 Agent 推理成本的构成公式

一个 Agent 系统的月 GPU 成本可以这样分解：

$$C_{monthly} = N_{gpu} \times C_{gpu/hr} \times 720 \approx \frac{QPS_{avg} \times T_{latency}}{U_{util}} \times C_{gpu/hr} \times 720$$

其中 $U_{util}$ 是 GPU 利用率（vLLM continuous batching 可推到 80-90%），$T_{latency}$ 是单请求平均服务时间。关键杠杆：

5.3 从 Scaling Law 到产品决策

Scaling Law（详见 D5 deep-dive `5-d2-scaling-law-product.html`）告诉我们：模型能力随参数量和训练 token 量呈幂律增长。但对 PM 来说，更有用的结论是：

  • 小模型 + 蒸馏 > 大模型量化：在固定预算下，一个蒸馏好的 7B 模型往往优于压到 INT2 的 70B 模型（ParetoQ 结论）
  • QPS 每 ↑10x，成本非线性下降：因为 GPU 固定成本分摊到更多请求上，continuous batching 让利用率突破 90%
  • 长上下文的边际成本极高：KV Cache 随序列长度线性增长，32K context 的 KV Cache 可能超过模型权重本身
本章核心结论：量化+Serving 是 Agent 产品的"基础设施税"。选对了（AWQ+vLLM+KV 量化），70B 模型可以在单张 H100 上以亚百毫秒延迟服务数百并发用户。选错了（BF16 原始模型 + naive serving），同样的硬件只能服务十几个用户。这个差距就是 PM 对技术选型的判断力的价值所在。
